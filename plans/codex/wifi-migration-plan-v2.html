OpenLens Wi-Fi migration Plan v2 2026-08-10 Claude review incorporated

OpenLens without ADB

Revised implementation plan for local Wi-Fi discovery, commitment-based one-time pairing, pinned mutual TLS, encrypted camera transport, and automatic reconnection.

Target experience: first use requires one matching six-digit code confirmed on both devices. Later use is: connect to the same local network, open both apps, and click Start camera on the PC. No ADB, cable, IP address, account, cloud service, or per-session phone confirmation.

2. User journey

2.1 First pairing

  1. Install and open both apps on the same trusted local network.
  2. Android requests Camera and any Android-version-appropriate local-network permission.
  3. The phone advertises OpenLens phone and opens a two-minute pairing window while the pairing screen is visible.
  4. The desktop discovers it and the user chooses Pair.
  5. An initial mutual TLS connection proves possession of both self-signed identity keys. This connection is isolated from normal strict-pinning contexts.
  6. The revised commit–reveal protocol produces the same six-digit code on phone and desktop.
  7. The user checks the codes and presses Codes match on both devices.
  8. Both sides atomically save the peer SPKI pin and friendly name, close pairing mode, and reconnect under strict pinned mutual TLS.

2.2 Normal use

  1. Open both apps on the same LAN.
  2. The desktop finds and strictly authenticates the paired phone.
  3. Click Start camera on the PC. No phone confirmation is required.
  4. Use the desktop preview, V4L2 device or native OBS source.
  5. Stop from the PC; the phone retains Android's privacy indicator, foreground notification and emergency Stop while streaming.

3. Scope and non-goals

In scope

  • Same-LAN discovery.
  • Encrypted mutual authentication.
  • One-time pairing and revocation.
  • Existing H.264 camera protocol over TLS.
  • Automatic rediscovery/reconnect.
  • Android and Qt pairing UI.
  • V4L2 and native OBS paths.
  • Manual pinned host fallback.

Out of scope

  • Internet or cloud relay.
  • WebRTC/STUN/TURN.
  • Unauthenticated LAN access.
  • iOS or audio.
  • Boot-time/background advertising.
  • Router configuration.
  • Public signing/identity decisions.
  • Supporting ADB as a user workflow.

4.1 Required abstractions

  • SessionTransport: read, write-all, close, peer identity and liveness.
  • TransportProvider: establish a normal authenticated session. Wi-Fi is production; ADB is a development-only source-set provider during migration.
  • DeviceDiscovery: found/updated/lost device records without camera logic.
  • IdentityStore: local key/certificate, peer SPKI pins, names, timestamps and revocation.
  • PairingCoordinator: isolated pairing TLS context, commitments, reveals, SAS, dual confirmation and atomic commit.
  • ConnectionState: one tested state model shared by UI and session logic.

The camera, encoder, protocol framing, decoder and output sinks remain transport-agnostic.

5. Threat model and invariants

5.1 Defend against

  • Passive LAN observers attempting to view video, controls or identity credentials.
  • Active LAN clients attempting to start/control the camera or impersonate a paired peer.
  • Active TLS-terminating MITM during first pairing, including certificate-grinding attackers.
  • Replay of pairing messages or confirmations from another attempt.
  • Friendly-name spoofing, duplicate mDNS names and IP address changes.
  • Connection floods, slow handshakes, oversized protocol messages and unbounded media queues.
  • Stale/changed identities after reinstall, reset or key loss.

5.2 Not claimed

  • Security if the user confirms different pairing codes or both endpoints are already compromised.
  • Protection from an attacker who can read either app's private storage or control its process.
  • Anonymity from LAN observers while the phone intentionally advertises an OpenLens service.
  • Availability against a network administrator who blocks multicast or device-to-device traffic.

5.3 Non-negotiable invariants

  1. Permissive certificate acceptance exists only in a short-lived pairing-specific SSLContext.
  2. Normal sessions require exact constant-time SPKI pin matches on both sides.
  3. Pairing records are committed only after both local users confirm the same SAS.
  4. All pairing values are bound to the TLS-presented keys, endpoint roles and unique attempt ID.
  5. Camera activation is impossible on pairing or unauthenticated sockets.
  6. Release builds contain no ADB session provider.

6. Revised pairing protocol

Security gate: this protocol replaces v1's grindable certificate-only SAS. It must receive independent cryptographic review and cross-language test vectors before Phase 2 implementation is approved.

6.1 Inputs and notation

NameDefinition
attempt256-bit cryptographically random pairing-attempt ID generated by the phone.
Np, NdIndependent 256-bit cryptographically random nonces generated by phone and desktop.
Pp, PdSHA-256 of the exact DER SubjectPublicKeyInfo presented by phone and desktop in the active TLS handshake.
roleOne-byte fixed role identifier: 0x01 phone, 0x02 desktop.
HSHA-256 over exact byte strings. Every construction has a distinct UTF-8 domain label and fixed-width fields.

6.2 Pairing connection prerequisites

  1. The phone pairing screen is visible, the two-minute pairing window is open, and no other pairing attempt exists.
  2. Both endpoints use TLS 1.3 and present their persistent self-signed identity certificate.
  3. The pairing-only trust managers accept structurally valid supported certificates solely to complete this enrollment handshake. They record the actual TLS peer SPKI; claimed fingerprints inside messages are never trusted.
  4. Each endpoint proves possession of its certificate private key through TLS CertificateVerify.

6.3 Symmetric commit-before-reveal exchange

Canonical key order is role-specific, never lexicographically sorted:
  keys = Pp || Pd

Phone commitment:
  Cp = H("OpenLens Pair v2 commit" || attempt || 0x01 || Np || keys)

Desktop commitment:
  Cd = H("OpenLens Pair v2 commit" || attempt || 0x02 || Nd || keys)

Exchange order:
  1. Phone → Desktop: PAIR_BEGIN(attempt, protocol version, display name)
  2. Both independently generate their nonce.
  3. Phone → Desktop: PAIR_COMMIT(role=phone, Cp)
  4. Desktop → Phone: PAIR_COMMIT(role=desktop, Cd)
  5. Phone → Desktop: PAIR_REVEAL(role=phone, Np)
  6. Desktop verifies Cp in constant time; aborts on failure.
  7. Desktop → Phone: PAIR_REVEAL(role=desktop, Nd)
  8. Phone verifies Cd in constant time; aborts on failure.
  9. Both compute transcript and SAS.

Both commitments are fixed before either party learns the other nonce. A TLS-terminating MITM must choose and prove its two certificate keys before the fresh committed values are revealed, preventing the certificate grinding attack from v1.

6.4 Transcript and six-digit SAS

T = H("OpenLens Pair v2 transcript" ||
      attempt || Pp || Pd || Cp || Cd || Np || Nd)

SAS_material = H("OpenLens Pair v2 sas" || T)

SAS = UniformSixDigits(SAS_material)

Display exactly six zero-padded decimal digits on both devices.

UniformSixDigits must be defined byte-for-byte in the protocol specification using rejection sampling, with shared Kotlin/C++ test vectors. Direct language-specific integer parsing or an unspecified modulo operation is forbidden.

6.5 Dual confirmation and atomic trust commit

  1. Both screens display the SAS, peer role/name, countdown and explicit Match/Cancel controls.
  2. Each sends PAIR_CONFIRM(attempt, T, matched=true) only after its local user confirms.
  3. Neither side writes a peer pin until it receives a valid confirmation bound to the same attempt and transcript T, and its own user has also confirmed.
  4. Both send PAIR_COMMIT_RESULT, atomically store peer device record + peer SPKI pin, then close the pairing TLS socket.
  5. A normal connection is established using a separate strict-pinning TLS context. Pairing success is not considered operational until this connection succeeds.
  6. Cancel, mismatch, timeout, socket loss or malformed data erases all provisional state.

6.6 Attempt controls

  • One active pairing socket and attempt per phone.
  • Two-minute pairing window; 30-second code-confirmation deadline.
  • At most five failed attempts per window, followed by a cooldown.
  • Maximum two concurrent TLS handshakes total and five new handshakes per 10 seconds per source address, with a global cap.
  • No pairing messages on strict normal-session listeners; no normal START/CONFIGURE on pairing listeners.

A six-digit SAS provides approximately 20 bits of human comparison strength. With commitments, fresh nonces, one active attempt and five-attempt limit, an online active attack is bounded near five chances in one million per pairing window. This remains subject to external review.

7. Identity, certificate and pin policy

7.1 Phone identity

  • Generate an EC P-256 signing key in Android Keystore using KeyGenParameterSpec; private key is non-exportable.
  • Create a self-signed X.509 identity certificate with a long validity window and no personal subject data.
  • Use a random installation UUID, never IMEI, Android ID, MAC address or ADB serial.

7.2 Desktop identity

  • Generate EC P-256 key/certificate through OpenSSL.
  • Write the private key atomically under the OpenLens configuration directory with mode 0600; reject broader permissions until repaired.
  • Exclude keys and trust databases from developer bundles, logs and backups created by OpenLens.

7.3 Trust semantics

  • Trust anchor is SHA-256(DER SubjectPublicKeyInfo), not the full certificate, CA chain, hostname or friendly name.
  • After pairing, custom strict trust managers require the exact pin in constant time and validate proof of private-key possession through TLS.
  • NotBefore/NotAfter do not silently invalidate an already pinned identity. Certificates are long-lived transport containers for pinned keys; validity dates are diagnostic.
  • Key change always produces Identity changed — re-pair required. Never replace a pin automatically.
  • Reissuing a certificate with the same SPKI may be accepted because the pin remains unchanged, subject to structural/key-use validation.
  • Identity reset and peer revocation are explicit UI operations with confirmation.

9.2 Lifecycle

  1. While the activity is visible, a bound controller advertises and accepts bounded TLS connections without opening the camera or starting a foreground service.
  2. After strict mTLS authentication and desktop START while the activity is foreground, promote CameraStreamingService using the camera FGS type and open Camera2.
  3. The camera FGS owns the active socket for the stream. Phase 0 must prove this remains alive while backgrounded.
  4. On Stop/error, close camera, encoder, TLS socket and FGS. Resume advertising only if the app remains intentionally available.
  5. Stop idle advertising when the app leaves the foreground. No boot receiver or hidden background listener.
FGS rule: do not add connectedDevice, FOREGROUND_SERVICE_CONNECTED_DEVICE or a qualifying network-state permission unless Phase 0 produces a reproducible failure with camera-only FGS and an ADR approves the change.

11. Protocol v2

Retain the proven bounded binary framing and media messages inside TLS. Increment the major version for Wi-Fi identity/pairing/session states.

PAIR_COMMITPairing TLS onlyRole-specific nonce commitment.
PAIR_REVEALAfter both commitsNonce reveal and verification.
PAIR_CONFIRMAfter SAS displayLocal confirmation bound to attempt/transcript.
PAIR_COMMIT_RESULTAfter dual confirmationAtomic trust-record completion.
AUTHENTICATED_HELLOStrict mTLS onlyVersion/features and identity-to-record binding.
START_STREAMAuthenticated idleExplicit camera activation/configuration.
BUSYAuthenticated connectionSingle-controller rejection without peer disclosure.

11.1 Protocol invariants

  • Pairing messages are rejected on normal listeners; camera messages are rejected before strict auth and START.
  • Unknown required messages, invalid transitions, wrong roles, repeated commits/reveals and cross-attempt IDs terminate the connection.
  • Every new message has canonical encoding and shared Kotlin/C++ valid/malformed fixtures.
  • Pairing metadata, TLS handshake and normal session have separate size/time limits.
  • Fuzz the plaintext parser/state machine after TLS termination.

12. Recovery, performance and latency

12.1 Reconnect

  • On socket loss, stop writes, show disconnect slate and rediscover the same identity for at most 60 seconds.
  • Require exact pinned SPKI on every reconnect; names and IP addresses never replace identity.
  • Fresh TLS and protocol handshakes, reconfigure encoder, request keyframe.
  • Bounded latest-biased encoded queue; no buffering an outage.
  • Manual host fallback remains strict-pin authenticated.

13. ADB migration and release removal

Current risk: the existing exported-activity/abstract-socket ADB path is not an acceptable release transport because a local app may be able to select/connect a session socket without its own camera permission.
  1. Phase 1 extracts transport interfaces and keeps ADB only to prove behavioral parity.
  2. Android ADB code moves to a development-only Gradle source set/flavor excluded from release APK compilation and manifest merging.
  3. Desktop ADB code is controlled by OPENLENS_ENABLE_ADB_TRANSPORT, ON only for explicit developer builds and OFF for release/package presets.
  4. Normal GUI never exposes ADB after Wi-Fi passes Phase 5.
  5. Release CI inspects APK manifest/classes and desktop dynamic dependencies/strings to prove no ADB launch/session provider is present.
  6. Public documentation and runtime dependency checks do not mention or require Platform Tools.
  7. Delete the fallback before beta unless a separate authenticated ADB design is approved.

14. Implementation phases

  • Measure current ADB glass-to-OBS median/p95 latency.
  • Prove Android NSD ↔ Avahi on reference LAN.
  • Prove Android Keystore EC certificate as TLS 1.3 server/client identity.
  • Prove camera-only FGS sustains backgrounded Wi-Fi streaming; reject/add connectedDevice via ADR.

  • Test a certificate-grinding MITM harness against v1 and v2.
  • Measure TLS throughput ≥25 Mbps for 15 minutes.
  • Evaluate omitting stable UUID from TXT.

Exit: reviewed ADR set; Phase 2 remains blocked until external crypto approval.

  • Extract transport/discovery/session interfaces.
  • Adapt current ADB path without changing media behavior.
  • Add compile-time dev-only ADB gates on Android and desktop.

  • Implement isolated pairing contexts and v2 symmetric commitments.
  • Implement dual confirmation, revocation, attempt limits and atomic storage.

15. Tests and release gates

15.1 Automated security tests

  • Kotlin/C++ identity, SPKI and SAS shared vectors.
  • Both commitments required before either reveal.
  • Wrong nonce, role, key order, attempt ID or transcript rejected.
  • v1 certificate-grinding relay succeeds in harness; v2 remains limited to online SAS guessing.
  • One-sided confirmation never persists trust.
  • Pairing TLS policy unavailable outside visible pairing window.
  • Strict pin success, mismatch, changed key and constant-time comparison tests.
  • Replay/cross-attempt messages rejected.
  • Handshake/concurrency/rate limits enforced.
  • Release build contains no ADB provider or exported ADB entry point.

15.2 Functional/physical gates

  • First matching-code pair succeeds; mismatch/cancel leaves no record.
  • Later use discovers/authenticates without code.
  • Unpaired LAN client cannot start/control/view camera.
  • Changed key requires explicit re-pair.
  • Normal app works on a clean host with no ADB installed.
  • Ten rotations preserve session.
  • Fifty Start/Stop cycles release every resource.
  • Twenty Wi-Fi disruptions recover within target when reachable.
  • 60-minute 1080p30 and two-hour OBS soaks retain metrics/recording.
  • Traffic capture shows encrypted local-only OpenLens traffic and no internet endpoints.
  • Router isolation, missing Avahi and permission denial produce useful errors.
  • Manual address path remains strict-pin protected.

15.3 Crypto review deliverables

  1. Formal transcript definition with byte lengths/endianness.
  2. At least ten canonical test vectors including leading-zero SAS.
  3. MITM/grinding/replay analysis.
  4. Independent reviewer approval or concrete replacement with a published pairing protocol.
  5. No implementation beyond experimental Phase 0 until approved.
