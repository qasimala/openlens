1. What version 2 changes

The two v1 plans agree on the important core: an installable Kotlin camera app, Camera2/MediaCodec hardware encoding, USB through ADB, a small desktop receiver, H.264 first, local-only privacy, and a measured phase-zero spike on the S24 Ultra. Their main disagreement is the first desktop sink. This v2 resolves it in favor of the shortest credible path to a working product on the actual Linux host.

Adopted from Claude v1

  • V4L2 virtual camera as the v0.1 OBS path.
  • Android abstract local socket through adb forward.
  • One-command desktop orchestration as the target UX.
  • scrcpy and native webcam baselines in phase zero.
  • Explicit Linux/CachyOS reference environment.

Retained from Codex v1

  • One versioned, bounded multiplexed protocol.
  • Camera2 rather than CameraX VideoCapture for the stream engine.
  • Native OBS plugin as a first-class planned sink.
  • Concrete latency, reconnect, soak, privacy, and release gates.
  • Capability-driven controls and honest OEM fallbacks.

Corrected or narrowed

  • S24 native-webcam support is a test question, not a fact.
  • 4K, 1080p60, audio, Wi-Fi, and direct physical-lens selection leave the MVP.
  • No automatic battery-optimization exemption request.
  • No silent sudo or kernel-module changes.
  • “OpenLens” remains a codename due to name collision.
V2 recommendation: implement the capture/transport/decoder as reusable components, ship a V4L2 sink first, then attach the same core to a native OBS source. This gets an OBS camera working without making OBS plugin ABI and packaging part of the first vertical slice.

2. Product definition

MVP user story: after one-time ADB and V4L2 setup, the user opens the phone app, connects USB, runs one desktop command, and selects Phone Camera as a Video Capture Device in OBS at stable 1080p30.

v0.1 scope

Must ship

  • Signed Android APK, minSdk 29 initially, targeting the current stable Android SDK.
  • Rear and front logical cameras, 720p30 and 1080p30 SDR presets.
  • Hardware H.264 encode, USB/ADB transport, desktop decode, V4L2 raw-frame output.
  • Zoom ratio, autofocus/tap focus, exposure compensation, torch, mirror, and orientation.
  • CLI device selection, diagnostics, reconnect, statistics, and actionable errors.
  • No account, cloud, telemetry, watermark, recording, or internet requirement.
  • CachyOS setup documentation plus a distro-neutral manual path.

Explicitly deferred

  • Audio and A/V synchronization.
  • 1080p60, 4K, HEVC, AV1, HDR/10-bit, and adaptive quality.
  • Direct physical-lens promises such as exact 3×/5× selection.
  • Wi-Fi, remote streaming, pairing, discovery, and TLS.
  • Windows/macOS, iOS, F-Droid, Play Store, and automatic updates.
  • Native OBS source plugin and multi-phone compositing.
  • Automatic privileged V4L2 setup.

Positioning

The project should not pretend the category is empty. scrcpy already streams cameras and can target V4L2 on Linux; some Android builds expose a platform webcam mode; commercial products offer polished phone-camera workflows. The product earns its existence through an installable open-source camera UI, explicit privacy, OBS-oriented controls and diagnostics, reproducible packages, and eventually a native OBS source. Phase zero must show a meaningful usability or capability advantage before the team invests in a duplicate transport stack.

Naming: do not publish under “OpenLens.” It is already associated with the Lens/OpenLens Kubernetes ecosystem. Use Phone Camera as a neutral UI label and choose the final project/package name before the first public tag.

Runtime rules

  • All queues are bounded. In low-latency mode, stale frames are dropped rather than accumulated.
  • Camera, encoder, socket, decoder, and sink each have explicit start/stop states and cancellation.
  • Presentation time uses one monotonic microsecond timebase. Wall-clock time is diagnostic metadata only.
  • A stream restart creates a new stream ID and begins with codec configuration plus a keyframe.
  • The desktop never silently changes phone quality or loads privileged host components.
  • Only one desktop client controls a phone session in v0.1.

4. USB session and wire protocol

Session establishment

  1. The CLI discovers devices with adb devices -l. It stops with specific guidance for none, offline, unauthorized, or multiple ready devices.
  2. The CLI generates a random session identifier and a valid abstract-socket name such as phonecam_7f31a2c9.
  3. The CLI launches the phone’s visible activity with the socket name and requested preset as intent extras. The app handles both a new launch and onNewIntent.
  4. The phone shows the request and requires the user’s Start action. On the first run it requests camera permission before starting any service.
  5. The activity starts a camera foreground service and creates LocalServerSocket with the session name.
  6. The CLI creates an ADB forwarding rule from an available host loopback port to the named localabstract socket, then connects.
  7. Both sides negotiate protocol version and stream settings. The phone returns requested versus applied settings.
  8. On Stop, disconnect, or timeout, each side closes its resources and the CLI removes only its own forwarding rule.
Why a per-session socket name: it prevents stale forwards and accidental cross-session attachment, while still avoiding a network listener on the phone. ADB’s authorized-computer relationship and the visible Start action are the v0.1 trust boundary.

Single binary envelope

Use one bidirectional stream. Every message has a fixed, big-endian header followed by a bounded payload. Capabilities and low-frequency controls can use UTF-8 JSON inside the envelope for inspectability; video payloads remain binary H.264 access units.

v0.1 messages

HELLO, HELLO_ACK, CAPABILITIES, CONFIGURE, CONFIGURED, VIDEO_CONFIG, VIDEO_FRAME, CONTROL, CONTROL_ACK, STATS, PING, PONG, ERROR, and END_STREAM.

Default video configuration

  • H.264/AVC, 1920×1080, 30 fps, 8 Mbps CBR, 8-bit SDR, 4:2:0.
  • Main profile when accepted, Baseline fallback; record the actual encoder/profile in CONFIGURED.
  • One-second keyframe interval. Request an immediate sync frame after reconnect or decoder discontinuity.
  • No B-frames when the encoder exposes a supported control. Never claim zero reorder latency without measurement.
  • VIDEO_CONFIG contains the exact codec-specific data emitted by MediaCodec; do not synthesize SPS/PPS when avoidable.
  • Maximum dimensions 4096×2160 and maximum encoded payload 8 MiB in v0.1, even though the UI exposes only 720p/1080p.

Parser/security requirements

  • Fuzz the desktop and Android parsers with truncated, oversized, unknown, duplicate, reordered, and corrupted messages.
  • Reject width/height/bitrate/FPS values outside negotiated capabilities and global safety limits.
  • No string from the phone is interpolated into a shell command. Invoke ADB with an argument vector.
  • Socket reads, writes, decoder work, and child processes are cancellable and time-bounded.
  • Normal logs hash or abbreviate ADB serials; verbose logs remain local and opt-in.

5. Android application design

Technology

  • Kotlin, Gradle Kotlin DSL, Jetpack Compose, coroutines, and AndroidX lifecycle components.
  • minSdk 29 initially. This keeps the first compatibility surface reasonable while covering Android 10+; lower it only after beta.
  • Camera2 for the actual stream. Do not use CameraX Recorder, because it targets muxed files and does not provide the exact low-latency encoder contract required here.
  • MediaCodec configured with a Surface input. The Camera2 repeating request targets preview and encoder surfaces directly, avoiding CPU YUV copies on the phone.
  • A user-started camera foreground service with the current required camera service type/permissions and a persistent Stop notification.

Capability-first camera model

Build presets from what the selected camera, output Surface combination, FPS ranges, and encoder actually advertise. Store both requested and applied values. On the S24 Ultra, enumerate logical cameras, physical IDs, focal lengths, zoom ratio range, stabilization, torch, exposure range, and supported constant FPS ranges in phase zero.

UI and lifecycle

  • States: Permission needed → Ready → Desktop requested connection → Starting → Streaming → Recovering → Stopped/Error.
  • The first screen explains that video stays local, USB debugging grants powerful computer access, and the camera is active only after Start.
  • Streaming screen shows preview, status, actual resolution/FPS/bitrate, elapsed time, camera, zoom, thermal warning, connection state, and a large Stop action.
  • Offer “dim preview” without disabling capture. Do not request battery-optimization exemption unless measured Samsung behavior proves it necessary; document vendor steps instead.
  • On Android versions with while-in-use restrictions, the visible activity starts the service. Do not attempt boot-start or hidden background camera launch.
  • Encoder/camera reconfiguration is transactional: stop output, increment stream ID, rebuild, emit config + keyframe, then resume.

6. Desktop core, CLI, and V4L2 sink

Desktop stack

  • C++17, CMake, threads or a small event loop, RAII resource ownership, and explicit cancellation tokens.
  • System Android Platform Tools for v0.1. Discover adb through PATH and an explicit --adb path; do not bundle it until licensing/update/security review.
  • FFmpeg libavcodec/libswscale dynamically linked. Software decode first; hardware decode only after it proves lower total latency and reliable format handling.
  • Linux V4L2 ioctls in a separate sink module. Negotiate I420/YU12 first, then NV12 or YUYV fallback based on the actual loopback device and OBS tests.

CLI contract

phonecam doctor                       # ADB, device, app, V4L2, FFmpeg, permissions
phonecam devices                      # ready/offline/unauthorized devices
phonecam cameras --device SERIAL      # phone capability summary
phonecam start                        # launch phone UI, forward, decode, V4L2 output
phonecam start --preset 720p30
phonecam start --device SERIAL --video /dev/video10
phonecam probe --json                 # machine-readable support data
phonecam receive --sink null --seconds 60  # transport/decode soak without V4L2

One-time V4L2 setup

  1. doctor detects whether v4l2loopback exists, is loaded, and exposes a usable output-only device.
  2. If missing, print distro-specific instructions and the exact proposed module parameters, including a chosen video_nr, card_label="Phone Camera", and exclusive_caps=1.
  3. The user performs the privileged package/module action. The CLI never invokes sudo itself in v0.1.
  4. doctor rechecks the result, formats supported by the loopback device, and whether OBS can see the device node.
  5. Persistent boot configuration is a separate explicit documentation step, not part of first-run mutation.

Reconnect behavior

  • On cable loss, stop feeding decoded frames and write a generated “Phone disconnected — reconnecting” frame at low rate so OBS retains the device.
  • Re-enumerate only the previously selected serial for 60 seconds. Do not attach a different phone automatically.
  • Re-launch the visible phone activity only when necessary and never bypass the user’s Start/permission requirement.
  • After new codec config + keyframe, flush the decoder, resume the sink, and report recovery duration.

7. OBS integration sequence

v0.1 — V4L2 source

  1. Run phonecam start.
  2. In OBS, add Video Capture Device (V4L2).
  3. Select Phone Camera, use the negotiated raw format, and set the source to the actual output dimensions/FPS.
  4. Keep the CLI running for the session. Camera controls remain on the phone or CLI in v0.1.

This is a genuine camera source in OBS and is reusable in browsers, Zoom, and other Linux camera consumers. Its tradeoff is one-time kernel-module setup and a separate CLI process.

v0.2 — native OBS source

Add a thin GPL-compatible OBS plugin using the official plugin template/toolchain. It links the same desktop core and replaces only the V4L2 sink. It registers Phone Camera as an asynchronous video source and exposes device, preset, camera, mirror, rotation, buffer mode, and live status in source properties.

  • Publish frames with correct format, dimensions, line sizes, timestamp, color matrix, and range.
  • Bound the plugin queue to at most two frames in low-latency mode.
  • Make “continue while hidden” the default for instant scene switches; expose stop-when-hidden as an option.
  • Share transport, decoder, reconnect, logging, and tests with the CLI; no second protocol client.
  • Keep the CLI and V4L2 sink supported because they are valuable diagnostics and enable non-OBS applications.

8. Delivery roadmap

Estimates assume one experienced developer and keep every phase demonstrable on the real S24 Ultra and CachyOS host.

Phase 0 — Evidence and stop/go decision

2–3 days

  • Record Android/One UI, kernel, CachyOS, OBS build/package, FFmpeg, ADB, cable, and USB controller versions.
  • Dump S24 camera/encoder capabilities, including logical/physical IDs and accepted Surface size/FPS pairs.
  • Benchmark scrcpy camera → V4L2 → OBS: setup time, quality, latency, controls, thermal behavior, and reconnect.
  • Check whether this exact S24 build offers a native USB webcam mode and benchmark it if present.
  • Prove Camera2 → MediaCodec → file, then validate the bitstream with FFmpeg.
  • Prove manual FFmpeg raw output → v4l2loopback → OBS and identify the best raw pixel format.
  • Choose a non-conflicting public project name or retain a private codename.

Exit: evidence shows a focused app can beat the baseline in UX/control/reliability, the S24 sustains 1080p30, and V4L2 is visible in the installed OBS build. Otherwise, reframe as an OBS/scrcpy integration.

Phase 1 — Repository and deterministic media fixtures

3–4 days

  • Scaffold Android, desktop core/CLI/sinks, protocol fixtures, docs, tests, and CI.
  • Freeze protocol v0 draft, safety limits, message fixtures, and parser tests.
  • Create deterministic H.264 samples and a synthetic-frame source so desktop work does not require the phone.
  • Build null/file/V4L2 sink interface and validate a synthetic pattern through OBS.
  • Add format/lint/unit-test/sanitizer jobs and dependency/license inventory generation.

Exit: both toolchains build from a clean checkout, parsers pass fixtures, and a synthetic source reaches OBS through V4L2.

Phase 2 — Android capture product slice

5–7 days

  • Implement permissions, preview, capability-derived presets, and visible session states.
  • Implement Camera2 dual-Surface session and MediaCodec output at 720p30/1080p30.
  • Add logical front/rear, zoom, focus, exposure, torch, mirror/orientation metadata.
  • Add camera foreground service, notification Stop, background/lock handling, and transactional reconfigure.
  • Add developer stats and 60-minute local encoder soak.

Exit: valid 1080p30 H.264 is produced for one hour with correct lifecycle and no unbounded memory/queue growth.

Phase 3 — USB vertical slice

5–7 days

  • Implement per-session abstract socket, ADB activity launch/forwarding, handshake, and configuration.
  • Implement desktop parser, decoder, normalized frame output, heartbeat, statistics, and cancellation.
  • Add device/authorization/multiple-device errors and safe forwarding-rule cleanup.
  • Run malformed-input/fuzz tests and 20 cable-pull recovery cycles.
  • Measure glass-to-decoder latency and remove hidden buffering before V4L2 integration.

Exit: phonecam receive --sink null sustains 1080p30 and reconnects to the same S24 without leaking resources.

Phase 4 — V4L2/OBS alpha

4–6 days

  • Implement V4L2 discovery, format negotiation, raw-frame pacing, placeholder frames, and errors.
  • Implement doctor and CachyOS plus distro-neutral setup documentation.
  • Validate OBS source add/remove, recording, streaming, scene switches, app restart, and CLI shutdown.
  • Tune decode/conversion/output for median glass-to-OBS latency below 150 ms.
  • Create an unprivileged install archive and clean uninstaller.

Exit: a clean supported Linux environment can follow the guide and record 60 minutes of 1080p30 phone video in OBS.

Phase 5 — Hardening and public v0.1 beta

5–7 days

  • Pass two-hour soak, 50 start/stop cycles, thermal test, screen lock, permission revoke, and USB reconnect suite.
  • Add redacted support bundle, JSON probe output, compatibility report, and actionable error copy.
  • Complete privacy/security review, license inventory, notices, SBOM, and signed release workflow.
  • Write build, install, OBS, troubleshooting, architecture, protocol, contributing, and security documentation.
  • Test one Pixel and one mid-range device before making broad Android claims; otherwise label S24-only beta clearly.

Exit: every beta gate passes and signed APK/CLI artifacts can be reproduced from the public source tag.

Phase 6 — Native OBS source v0.2

7–10 days after v0.1 stabilizes

  • Scaffold official OBS plugin toolchain and pin supported OBS versions.
  • Attach desktop core to asynchronous source output with correct timestamps/color metadata.
  • Add source properties, live status, reconnect placeholder, scene lifecycle, and bounded queue.
  • Package/test native Linux plugin, then use it as the base for Windows/macOS ports.

Exit: Phone Camera is directly addable inside OBS and matches or beats V4L2 latency/reliability without duplicating core logic.

Post-v0.2 order

Next audio synchronization and 1080p60 certification; Later Windows OBS, HEVC, encrypted Wi-Fi pairing, macOS OBS, F-Droid, 4K/HDR, and OS-wide virtual cameras.

9. Verification strategy

Automated test pyramid

Protocol/core

  • Round-trip and golden fixtures.
  • Fuzzing and hard allocation limits.
  • Reconnect/state-machine race tests.
  • Sanitizers and cancellation tests.
  • Timestamp monotonicity and queue bounds.

Android

  • Preset capability selection.
  • Camera/encoder state transitions.
  • Permission and service lifecycle.
  • Control clamp/applied-value logic.
  • Fake encoded source transport tests.

Desktop/sinks

  • Fake ADB process outcomes.
  • Golden H.264 decode and corrupt input.
  • Pixel format/color conversion.
  • V4L2 short writes/device removal.
  • Synthetic frame to OBS smoke test.

License and provenance

  • Provisional project license: GPL-3.0-or-later. Confirm before the first public commit with a complete SPDX dependency inventory.
  • Use system/dynamic LGPL-compatible FFmpeg libraries for release packaging where practical; record actual build configuration and linked library licenses.
  • Study scrcpy as prior art but implement independently first. Any copied/modified Apache-2.0 material must retain copyright and license notices and be recorded in NOTICE.
  • Do not assume the OBS plugin template’s files can be relicensed. Preserve their licensing and ensure the final combined plugin distribution is compatible.
  • Use DCO sign-off rather than a custom CLA initially. Add SPDX headers and automated license policy checks.

Public beta artifacts

  • Signed Android APK, Linux CLI archive/package, source archive, SHA-256 checksums, SBOMs, and release notes.
  • Compatibility table stating tested phone, Android build, host distro/kernel, OBS package/version, ADB, and FFmpeg.
  • Reproducible build instructions and CI provenance. No opaque binary updater or backend.
  • README with honest comparison to scrcpy and available platform webcam mode, plus clear project limitations.
  • Issue forms for bugs and device reports that request the redacted phonecam probe --json output.

Release policy

Protocol major versions remain compatible within a stable release line. Phone and desktop negotiate minor features. Security fixes can remove unsafe compatibility. Public releases require physical S24 acceptance evidence in addition to CI. No component auto-updates in v0.x; releases surface mismatched versions with a clear download link.

12. Inputs and gates for the final v3

The final v3 should be based on evidence and maintainer preferences, not another purely architectural merge. These are the decisions that remain intentionally open until Claude’s v2 and a short hardware inspection are available.

Evidence required before v3 freezes implementation

  1. Exact CachyOS kernel and OBS package type/version.
  2. Exact S24 Ultra Android/One UI build and camera capability dump.
  3. Whether native USB webcam mode appears on this exact device/build.
  4. scrcpy camera→V4L2 latency, quality, controls, thermal, and setup experience.
  5. V4L2 formats accepted by the installed OBS build.
  6. Camera2 + MediaCodec sustained 1080p30 result and actual encoder name/profile.

Maintainer choices for v3

  1. Final public name and application/package identifiers.
  2. Whether v0.1 must work only on S24/CachyOS or claim broader Android/Linux support.
  3. C++17 desktop default versus Rust if maintainer expertise strongly favors it.
  4. Whether the native OBS plugin moves into v0.1 despite the additional schedule.
  5. Copyleft preference and final license after dependency review.
  6. Whether microphone audio is required for the first public beta.
