1. Final verdict and frozen decisions

Claude v2 and Codex v2 converge on the same core architecture. V3 removes the remaining ambiguity and deliberately limits the first release so implementation has one path, one desktop toolchain, one protocol, and measurable completion gates.

v0.1 alpha

Phone → USB/ADB → desktop CLI → V4L2 → OBS. This is the fastest complete proof and remains the system-wide Linux-camera path.

v0.2 beta

Phone → USB/ADB → shared desktop core → native OBS source. This is the flagship OBS experience and future Windows/macOS path.

Not in either

Audio, Wi-Fi, 720p60 promises, 1080p60, 4K, HEVC, HDR, physical-lens guarantees, and non-Linux packages.

2. Product contract and release scope

Core promise: after one-time ADB and V4L2 prerequisites, connect the S24 Ultra by USB, open the app, press Start, run one desktop command, and select Phone Camera in OBS at stable 1080p30—with no account, cloud, telemetry, watermark, or Wi-Fi dependency.

v0.1 alpha must include

  • Android APK tested and certified on the S24 Ultra.
  • Rear/front logical camera, 720p30 and 1080p30 presets.
  • Hardware H.264 encode, USB/ADB transport, software H.264 decode.
  • V4L2 I420/NV12/YUYV negotiation based on the actual OBS path.
  • Zoom, autofocus/tap focus, exposure compensation, torch, mirror, orientation.
  • Device selection, reconnect, doctor command, statistics, support bundle.
  • CachyOS-specific and distro-neutral setup/troubleshooting docs.

v0.2 beta adds

  • Native Linux OBS asynchronous video-source plugin.
  • Device, preset, bitrate, camera, mirror, rotation, and buffer source properties.
  • Live connection/statistics status and actionable source errors.
  • Correct libobs timestamps, pixel format, color space, matrix, and range.
  • Scene lifecycle, hidden-source behavior, duplicate-source guard, clean shutdown.
  • Plugin package/installer, compatibility matrix, and Flatpak limitations.

Non-negotiable runtime rules

  • Every queue has a documented maximum. Video favors dropping stale work over increasing latency.
  • All blocking operations support cancellation and bounded shutdown.
  • Media uses monotonic microsecond timestamps. Wall-clock time is diagnostic only.
  • Every reconfigure creates a new stream ID and starts with codec configuration plus a keyframe.
  • Only one active controlling desktop client per phone in v0.x.
  • No hidden quality downgrade, privileged host mutation, automatic recording, or network fallback.

4. ADB session and protocol v0.1

Connection lifecycle

  1. The CLI/plugin enumerates ADB and requires one ready device or an explicit serial.
  2. It creates a random alphanumeric session ID and abstract name such as openlens_7f31a2c9.
  3. It launches the app’s visible activity with fixed, safely encoded intent extras for the session and requested preset.
  4. The app requests permission if needed, shows the connection request, and requires the user to press Start.
  5. The activity starts the correctly typed camera foreground service; the service creates LocalServerSocket using the session name.
  6. The desktop forwards a free host-loopback port to that localabstract socket and connects. It retries port selection on a race.
  7. HELLO/HELLO_ACK, capabilities, and requested/applied configuration complete before video begins.
  8. Heartbeat failure tears down codec/socket/decoder state. Reconnect targets only the same serial and creates a new stream ID.
  9. Shutdown removes only the forwarding rule created for this session.

36-byte base header

All integer fields are unsigned and big-endian. Payload limits are checked before allocation.

FieldBytesMeaning
Magic4PHCM
Major / minor1 + 1Major incompatibility fails; minor features negotiate.

PTS microseconds8Monotonic media time; zero when not applicable.
Payload length4Validated against per-message/global maximum.

Messages and payloads

HELLO, HELLO_ACK, CAPABILITIES, CONFIGURE, CONFIGURED, VIDEO_CONFIG, VIDEO_FRAME, CONTROL, CONTROL_ACK, STATS, PING, PONG, ERROR, and END_STREAM.

  • Capabilities, configuration, controls, acknowledgements, statistics, and errors use versioned UTF-8 JSON schemas inside the binary envelope.
  • Video messages contain MediaCodec-produced codec configuration or one encoded access unit; no base64 and no JSON video data.
  • Global v0.1 payload maximum: 8 MiB. Control/metadata maximum: 256 KiB. Dimensions maximum: 4096×2160. UI exposes only certified presets.
  • Unknown optional messages are skipped. Unknown required messages end the connection with a version error.
  • Every control ACK reports requested value, applied value, and a stable error code/reason when clamped or unsupported.

Default encoder contract

  • 1920×1080, 30 fps, 8 Mbps CBR, H.264 Main profile when accepted, Baseline fallback, SDR 4:2:0.
  • One-second keyframe interval; request sync frame after discontinuity/reconnect.
  • No B-frames where supported and verified. Report actual encoder/profile/level/bitrate mode.
  • Use the exact codec-specific data emitted by MediaCodec. A new stream starts with VIDEO_CONFIG plus a keyframe.
  • 720p30 default fallback at 4 Mbps. Bitrate is user-adjustable within capability and safety limits only after the stable presets work.

5. Android application

Stack and modules

  • Kotlin, Gradle Kotlin DSL, Jetpack Compose, coroutines, immutable UI/session state, minSdk 31.
  • app: activity, Compose UI, runtime permissions, foreground-service lifecycle.
  • camera: Camera2 capabilities, preset validation, session, controls, capture results.
  • encoder: MediaCodec selection/configuration/input Surface/output buffers.
  • protocol: message models, framing, bounded serialization/parser, fixtures.

Capture pipeline

  1. Enumerate the selected logical camera and derive allowed Surface size/FPS combinations.
  2. Configure MediaCodec encoder and obtain its input Surface.
  3. Create a Camera2 TEMPLATE_RECORD repeating request targeting preview and encoder surfaces.
  4. Use an advertised constant AE FPS range; continuous-video AF; compatible stabilization default.
  5. Drain encoder asynchronously, translate flags/PTS, and enqueue bounded protocol messages.
  6. On setting changes requiring rebuild, stop transactionally, increment stream ID, recreate, emit config/keyframe, resume.

Lifecycle and UI

  • Permission needed → Ready → Desktop request → Waiting for Start → Starting → Streaming → Recovering → Error/Stopped.
  • Camera permission is requested in context. Microphone permission does not exist until audio is implemented.
  • Streaming starts from a visible activity and uses current camera foreground-service declarations and a persistent Stop notification.
  • No boot start, hidden start, or background bypass. Screen lock/background behavior is verified on the exact One UI build.
  • Streaming view shows preview, camera, zoom, requested/actual FPS, bitrate, encoder, keyframes, drops, thermal state, elapsed time, and Stop.
  • “Dim preview” is available. Do not request a battery-optimization exemption unless measurement proves it necessary.

6. Desktop core and CLI

Toolchain

  • C++20, CMake, Ninja in development, clang-format, clang-tidy, warnings-as-errors in project code.
  • RAII for sockets/processes/codec/frames/device handles; std::span for bounded views; checked size arithmetic.
  • ASan/UBSan debug CI, fuzz targets for framing/JSON schema boundaries, and hardened release flags supported by the toolchain.
  • System adb and dynamically linked FFmpeg libraries initially. No bundled Platform Tools or codec libraries before packaging review.
  • FFmpeg software H.264 decoder first. Hardware decode is an optimization only if measurements improve latency/CPU without reliability loss.

CLI surface

openlens doctor                         # prerequisites, device, app, V4L2, FFmpeg
openlens devices                        # ready/offline/unauthorized devices
openlens cameras --device SERIAL        # capability report
openlens start                          # launch app, connect, decode, write V4L2
openlens start --preset 720p30
openlens start --device SERIAL --video /dev/video10
openlens probe --json                   # redacted support/compatibility data
openlens receive --sink null --seconds 60
openlens receive --sink file --output explicit.h264

ADB manager

  • Locate adb through PATH or explicit setting; check version; parse devices into ready/offline/unauthorized states.
  • Require explicit selection with multiple ready devices and persist only a user-selected serial.
  • Invoke processes with argument vectors, never a shell command assembled from device data.
  • Generate safe session/socket names, launch visible activity, create/remove only owned forwards, capture actionable stderr.
  • Redact/harden serials in default logs and JSON support output.

Decode and sink pipeline

  • Parser emits codec config/access units; decoder flushes on new stream ID and waits for config/keyframe.
  • Normalize to a frame structure carrying planes, strides, width/height, PTS, color space/matrix/range, and discontinuity.
  • Sink interface supports configure, push, placeholder, flush, and stop.
  • Low-latency queue is at most two decoded frames. When behind, drop safely at stream boundaries rather than replay stale video.
  • Per-stage statistics: receive bitrate, sequence gaps, queue depth, decode time/errors, conversion time, sink write time, actual FPS.

7. Linux V4L2 alpha and native OBS beta

v0.1 V4L2 path

  1. openlens doctor checks for a loopback module/device and tests supported raw formats.
  2. If absent, it prints reviewed CachyOS and generic Linux instructions plus the exact proposed video_nr, label, and exclusive_caps=1 parameters.
  3. The user performs privileged package/module actions. The program does not invoke sudo, edit boot configuration, or load a module silently.
  4. The V4L2 sink negotiates the phase-zero-proven raw format—prefer I420 when OBS/device support is correct; otherwise NV12/YUYV.
  5. OBS adds Video Capture Device (V4L2) → Phone Camera. The CLI owns the live session and controls.
  6. On disconnect, the sink emits a low-rate generated reconnect slate so OBS retains the source/device.

v0.2 native source

  • Use the official OBS build/toolchain guidance and only template code whose license is reviewed and preserved.
  • Register one asynchronous source named Phone Camera. Share ADB/protocol/decode/reconnect through desktop core.
  • Each physical phone permits one active controlling source. A duplicate source shows a clear “device already in use” state.
  • Properties: device, preset, bitrate, facing, zoom, focus mode, exposure, torch, mirror, rotation, buffer mode, stop-when-hidden, status.
  • Publish correct frame timestamps and color metadata. Reconfigure on a new stream/config/keyframe boundary.
  • Keep running while hidden by default for instant scene changes; allow opt-in stop-when-hidden.
  • Hold last frame for at most two seconds after disconnect, then show a generated disconnected slate while reconnecting.
  • Test native package first. Document Flatpak host-ADB/plugin-location constraints rather than claiming unsupported packaging.

Why both paths remain

V4L2 enables all Linux camera consumers and isolates upstream debugging from OBS. The plugin gives the intended OBS user experience and is the Windows/macOS entry point. Neither reimplements transport or decode.

9. Phased build roadmap

Estimates assume one experienced developer. V0.1 alpha is approximately 5–7 weeks after phase-zero approval; v0.2 beta adds approximately 2 weeks.

Phase 0 — Baseline, hardware evidence, stop/go

2–3 working days · mandatory before product scaffolding

  • Record S24 Android/One UI build, USB mode/cable/controller, CachyOS kernel, ADB/FFmpeg, OBS version and package type.
  • Run scrcpy camera → V4L2 → OBS and measure setup, quality, latency, CPU, thermal, controls, reconnect.
  • Check whether this exact S24 build exposes a native USB webcam mode; benchmark it if present.
  • Create capability-dump spike: logical/physical cameras, focal lengths, zoom, sizes/FPS, encoder names/profiles/modes.
  • Prove Camera2 → MediaCodec 1080p30 for 30 minutes and validate exact H.264 output.
  • Prove synthetic/FFmpeg raw frames → v4l2loopback → installed OBS; test I420/NV12/YUYV.
  • Write ADR-001 stop/go and the measured comparison.

Exit: continue only if the custom app can materially improve controls, OBS workflow, diagnostics, or reliability. If not, reframe the project as a native OBS integration and UI around scrcpy.

Phase 1 — Foundations and deterministic fixtures

3–4 working days

  • Create monorepo modules, toolchains, CI, formatting, static analysis, tests, and temporary private IDs.
  • Write ADR-002 architecture/sinks, ADR-003 C++20, ADR-004 provisional license, ADR-005 protocol.
  • Implement 36-byte framing in Kotlin/C++ with golden valid/malformed cross-language fixtures and fuzz targets.
  • Create deterministic H.264 samples plus synthetic source and null/file/sink contract.
  • Send synthetic moving frames through V4L2 into OBS without the phone.

Exit: clean builds pass; cross-language fixtures match byte-for-byte; synthetic OBS video is stable.

Phase 2 — Android capture engine

5–7 working days

  • Permissions, preview, capability-derived 720p30/1080p30 presets, visible session states.
  • Camera2 dual-Surface capture and MediaCodec H.264 output with actual-format reporting.
  • Rear/front, logical zoom, focus, exposure, torch, mirror, and orientation metadata.
  • Foreground service, notification Stop, lock/background handling, transactional reconfigure.
  • Developer statistics and one-hour local encoder soak.

Exit: the APK produces valid 1080p30 for one hour without leaks/unbounded queues and handles 50 local start/stops.

Phase 3 — USB transport and desktop vertical slice

5–7 working days

  • Per-session abstract socket, visible ADB launch, forward ownership, handshake, controls, heartbeat.
  • Desktop ADB manager, bounded parser, FFmpeg decode, normalized frames, stats, cancellation, reconnect.
  • CLI devices/cameras/probe/receive verbs and JSON output.
  • Malformed/fuzz suite plus no-device/offline/unauthorized/multi-device/app-absent/codec-reset matrix.
  • Twenty cable-pull recoveries and glass-to-desktop latency measurement.

Exit: openlens receive --sink null sustains 1080p30 for one hour and reconnects to the same phone without leaked resources.

Phase 4 — V4L2/OBS v0.1 alpha

4–6 working days

  • V4L2 discovery, format negotiation, pacing, reconnect slate, write/device-removal errors.
  • Doctor command and reviewed CachyOS/generic Linux prerequisite flow.
  • OBS recording/streaming/scene tests; two-hour soak; 50 cycles; 20 cable pulls.
  • Latency tuning to alpha gates; redacted support bundle and compatibility report.
  • Signed APK + CLI alpha artifacts, checksums, SBOM, build/setup/troubleshooting docs.

Exit: every v0.1 gate passes on the reference S24/CachyOS/OBS matrix. Tag v0.1.0-alpha.1.

  • Review OBS/template licenses/toolchain; scaffold plugin and pin supported OBS range.
  • Attach desktop core to asynchronous source output with correct timestamps/color metadata.
  • Source properties/status, duplicate guard, scene lifecycle, reconnect/placeholder UX.
  • Plugin install/uninstall package that leaves unrelated OBS files untouched.
  • Native-package test matrix, two-hour OBS recording, beta latency gates, public name/package ID freeze.

11. Privacy, security, and open source

Published promises

  • No account, advertisements, analytics, telemetry, cloud service, watermark, or required internet.
  • USB mode uses ADB authorization, per-session device abstract socket, host loopback forward, and explicit visible Start.
  • The camera never starts at boot or secretly in the background; persistent notification while active.
  • No automatic recording. Diagnostic frame/bitstream capture is explicit and saved to a user-selected path.
  • Logs redact device serials and exclude frame contents. Support bundles stay local until the user shares them.
  • Signed artifacts, checksums, SBOM, least-privilege CI, and private vulnerability reporting.

Threat controls

  • Protocol input is untrusted: hard payload/dimension limits, checked arithmetic, fuzzing, sanitizers, timeouts.
  • ADB is invoked without a shell and with fixed/generated arguments. No phone-provided string becomes executable text.
  • Second client is rejected; session identifiers are random and short-lived; forwards are removed on normal shutdown.
  • Reconnect is pinned to the same selected serial and never falls back to LAN or a different phone.
  • Kernel/module setup is documented, explicit, and outside the unprivileged program.

Open-source baseline

  • LICENSE, NOTICE, SPDX policy/headers, generated dependency inventory.
  • README, CONTRIBUTING, CODE_OF_CONDUCT, SECURITY, DCO sign-off, issue forms.
  • Honest comparison with scrcpy, any available native webcam mode, and proprietary alternatives.
  • Device-report form collecting redacted probe output and tested preset—not unstructured “doesn’t work” reports.
  • Do not claim general Android/Linux support until a Samsung, Pixel, and mid-range phone plus multiple supported OBS/Linux configurations pass.

14. Go-ahead execution contract

When approval is given, implementation begins with Phase 0 only. Phase 0 is evidence-gathering and reversible prototyping on the S24 Ultra/CachyOS machine. Its result is the stop/go ADR. If the result is “go,” work continues through the frozen v3 architecture; if “reframe,” the implementation switches to a scrcpy-based OBS integration without preserving sunk-code assumptions.

Actions authorized by a build go-ahead

  • Create the repository structure, spike Android project, C++ proof tools, tests, ADRs, and documentation described here.
  • Inspect local Android/OBS/ADB/FFmpeg/kernel/V4L2 state and build/run unprivileged local prototypes.
  • Build/install a debug APK to the explicitly connected S24 through the already-authorized ADB relationship.
  • Run camera/encoder/latency/soak/reconnect tests and create local diagnostic artifacts.

Actions that still require explicit approval when encountered

  • Installing system packages, loading/configuring kernel modules, or any privileged host mutation.
  • Publishing a repository/release, creating external accounts/domains, sending data, or distributing artifacts.
  • Choosing and registering the public name, permanent application ID, signing identity, or domain.
  • Any destructive cleanup outside generated build artifacts.

Phase-zero output before major product work

  1. Environment/capability report.
  2. scrcpy/native alternative comparison.
  3. Camera2/MediaCodec proof result.
  4. V4L2/OBS format proof result.
  5. Measured stop/go ADR and any necessary v3 amendment.
