Working product & engineering plan

Android phone camera source for OBS

A privacy-first, open-source system that turns an Android phone—starting with a Samsung Galaxy S24 Ultra—into a low-latency OBS Studio camera over a USB debugging connection.

1. Recommended direction

Build three pieces in one repository: an Android camera app, a reusable desktop connection/decoder core, and a thin native OBS source plugin. The phone captures frames with Camera2, encodes H.264 in hardware with MediaCodec, and sends the compressed frames through a local TCP socket. The desktop creates an adb forward tunnel over USB, receives and decodes the stream, and hands frames directly to OBS as a source named Phone Camera.

MVP promise

Install the APK and OBS plugin, connect the S24 Ultra by USB, approve debugging, press Start, then add Phone Camera in OBS.

First release target

Stable 1080p30 SDR H.264, video-only, rear/front camera, zoom, focus, exposure, rotation, reconnect, and useful diagnostics.

Deliberate deferrals

4K, HDR, wireless mode, microphone audio, system-wide virtual webcam, iOS, multiple simultaneous phones, and app-store distribution.

Product naming gate: “OpenLens” should remain a repository codename only until a naming search is completed. The name is already strongly associated with the Lens/OpenLens Kubernetes ecosystem. Pick a distinct public name before package IDs, domains, signing identities, and release artwork become expensive to change.

Reality check and differentiation

scrcpy already supports Android camera streaming and, on Linux, a V4L2 webcam sink. Use it as a performance and usability baseline in week zero, not as a reason to abandon the product. A focused project can still differentiate through a native OBS source, an installed phone UI with live camera controls, first-class reconnect/diagnostics, consistent packaging, and a clear privacy model. Avoid copying scrcpy code during the first implementation; if code is later reused, preserve its Apache-2.0 notices and complete a license-compatibility review.

2. Product scope and release gates

Primary user story

“As an OBS user, I can plug my Android phone into my computer, open the phone app, add the phone as an OBS source, and get a reliable, low-latency camera image without an account, cloud service, watermark, proprietary driver, or Wi-Fi dependency.”

In the MVP

  • Android APK, initially targeting Android 12+ and tested first on the Galaxy S24 Ultra.
  • USB debugging transport through the user’s installed Android Platform Tools.
  • Linux OBS Studio plugin as the reference desktop build.
  • H.264/AVC SDR at 720p30 and 1080p30; 720p60 only if capability tests pass.
  • Rear/front selection, logical-camera zoom, autofocus, tap-to-focus, exposure compensation, torch, rotation, and mirror.
  • Automatic reconnect after cable removal, app restart, or OBS source reactivation.
  • Local-only operation with no account, telemetry, internet requirement, or remote listener.
  • Diagnostics: selected device, transport status, actual resolution/FPS/bitrate, frame drops, decode errors, and copyable support bundle.

Out of MVP

  • Audio; ship video correctly before adding microphone permissions and A/V synchronization.
  • 4K, HEVC, AV1, HDR/10-bit, LOG, portrait blur, stabilization modes, and multi-camera compositing.
  • Wi-Fi discovery/transport, remote internet streaming, or any cloud relay.
  • A system-wide webcam visible to Zoom, Teams, browsers, and other apps.
  • Windows/macOS packages. Keep the core portable, then add these after Linux beta proves the protocol.
  • Google Play publishing, auto-update, crash collection, and signed package repository.
  • iOS support.

Platform sequencing

The current development environment suggests Linux-first because it offers the fastest local iteration path and OBS has an official plugin toolchain for Ubuntu. In phase 0, confirm the actual desktop operating system used with the S24 Ultra. If it is Windows, keep the same architecture but make Windows the reference package and move Linux to the second platform. Do not try to ship all three desktop platforms before the protocol and reconnect behavior are stable.

3. Technical architecture

Camera API

Camera2 for the streaming engine. It can feed the encoder input Surface directly and exposes the manual/physical-camera controls needed for a serious camera source. CameraX may still be used for simple preview/UI helpers if it does not constrain the stream.

Video codec

H.264/AVC, 8-bit SDR. Hardware encoding is widespread and decoding is straightforward. Start with Main profile when supported, CBR, a one-second keyframe interval, and no B-frames where the device encoder permits it.

Transport

Versioned binary frames over TCP through adb forward. This is simple to debug, bidirectional for controls, and does not expose a LAN port. ADB already handles USB device discovery and the trusted-computer prompt.

Android application

  • Language/UI: Kotlin, Gradle Kotlin DSL, Jetpack Compose, coroutines, and immutable session state.
  • Minimum/target SDK: begin with minSdk 31 (Android 12) to reduce compatibility work; use the current stable target SDK when implementation starts. Lower minSdk only after the beta architecture is stable.
  • Camera session: a Camera2 repeating request targets both the on-phone preview surface and MediaCodec.createInputSurface(). Use TEMPLATE_RECORD, continuous video AF, an advertised constant FPS range, and capability-derived sizes.
  • Lens model: enumerate logical cameras, physical IDs, focal lengths, sensor orientation, zoom ratio range, supported sizes/FPS, stabilization, torch, and manual-control ranges. Prefer smooth logical-camera zoom on Samsung; only promise direct physical-lens selection when the device actually exposes and accepts it.
  • Encoder defaults: 1920×1080, 30 fps, 8 Mbps CBR, H.264 Main or Baseline fallback, one-second I-frame interval, surface color input, and repeated codec configuration after reconnect. Make bitrate adjustable from 2–20 Mbps.
  • Frame timestamps: preserve monotonic presentation timestamps in microseconds; never use wall-clock time for pacing. Reset the session timeline on an explicit stream restart.
  • Lifetime: streaming starts only from a visible user action. If capture continues while the activity is not visible or the screen is off, run a camera foreground service with the required Android 14+ service type and permanent “Camera streaming” notification.
  • UI states: No permission → Ready → Waiting for desktop → Streaming → Recovering → Error. Each error must include a user action, not only an exception string.
  • Screen behavior: offer “dim preview while streaming” and “keep streaming when screen locks” separately. Verify Samsung power-management behavior rather than assuming foreground service alone prevents termination.

Desktop core and diagnostic CLI

  • Implementation: modern C++ (matching the OBS plugin toolchain), CMake, and a small platform abstraction for process launch, sockets, timing, and paths.
  • ADB manager: locate adb, query adb devices -l, represent unauthorized/offline/ready states, require serial selection if multiple devices exist, establish/remove only this app’s forwarding rule, and capture actionable error output.
  • Transport client: bounded reads, protocol version negotiation, maximum-frame checks, cancellation, heartbeat, and exponential reconnect capped at five seconds.
  • Decoder: use FFmpeg/libavcodec H.264 decoding with hardware decode as a later optimization. Convert to OBS-friendly NV12 or I420 while preserving color range/matrix metadata.
  • CLI: phonecam-cli list, probe, receive, and doctor. It should validate the whole path without OBS, write a short Annex-B diagnostic capture only when explicitly requested, and provide machine-readable JSON output for CI.
  • Privacy: redact ADB serials in logs by default; support an explicit verbose mode. Never upload support bundles automatically.

OBS plugin

  • Start from the concepts and build layout in the official OBS plugin template, but make license provenance explicit.
  • Register one asynchronous video source called Phone Camera. Each source instance owns a connection session and uses the shared desktop core.
  • Source properties: Android device, resolution/FPS preset, bitrate, camera, mirror, rotation, buffer mode, and a read-only status panel.
  • Emit decoded frames through libobs with correct timestamp, format, color space, range, width, height, and line sizes. Avoid a frame queue longer than two frames in low-latency mode.
  • Stop decoding when the source is destroyed. Make “stop when hidden” configurable; default to continuing so scene switches are instant.
  • On resolution/rotation changes, reconfigure the source cleanly at the next keyframe. Show the last good frame for at most two seconds during a reconnect, then switch to a clear “Disconnected” placeholder.
  • Use OBS’s logging API and prefix all messages consistently. Never log raw frame data or the full device serial at normal log levels.

4. Transport and protocol design

Connection flow

  1. The user opens the phone app, grants camera permission, selects a preset, and presses Start.
  2. The app starts a loopback-only server on a fixed device port and displays Waiting for desktop. No socket listens on Wi-Fi interfaces.
  3. The OBS source enumerates ADB devices and checks for exactly one authorized target or uses the serial selected in source properties.
  4. The plugin creates a forwarding rule from a free host loopback port to the fixed device loopback port using adb -s SERIAL forward.
  5. The plugin connects and sends HELLO with supported protocol versions and requested stream settings.
  6. The phone replies with capabilities and an accepted configuration, starts Camera2/MediaCodec, then sends codec configuration followed by access units.
  7. The plugin decodes and publishes frames. Control changes travel back over the same socket and are acknowledged with the applied value.
  8. Either side sends a heartbeat. On failure, both sides tear down codec/socket state cleanly and enter a bounded reconnect loop.
Security boundary: ADB’s authorized-computer relationship plus an explicit Start action on the unlocked phone is sufficient for the USB-only MVP. Bind the phone and desktop sockets to loopback, reject a second client by default, remove the forwarding rule at shutdown, and never fall back to LAN transport silently.

Wire framing

Use a small, documented, big-endian binary header followed by a length-bounded payload. Keep the envelope independent of JSON so video frames do not need escaping or base64. JSON or CBOR is acceptable inside low-frequency control payloads, but freeze one representation before beta.

FieldSuggested sizePurpose
Magic4 bytesPHCM; rejects accidental/misaligned input.
Protocol version2 bytesMajor/minor negotiation; incompatible major versions fail clearly.
Message type + flags2 + 2 bytesFrame kind, keyframe/config/end-of-stream flags.
Stream ID4 bytesSeparates restarted streams and permits future audio.
Sequence8 bytesDetects loss, duplication, and reconnect boundaries.
PTS8 bytesMonotonic presentation timestamp in microseconds.
Payload length4 bytesMust be validated against a hard maximum before allocation.
PayloadVariableControl data, capabilities, codec extradata, or one encoded access unit.

Required message set

HELLO, CAPABILITIES, CONFIGURE, CONFIGURED, VIDEO_CONFIG, VIDEO_FRAME, CONTROL, CONTROL_ACK, STATS, PING, PONG, ERROR, and END_STREAM.

Protocol invariants

  • A new stream ID always begins with VIDEO_CONFIG and a keyframe before dependent frames.
  • Unknown optional message types are skipped safely; unknown required types end the session with a version error.
  • Every user-visible control response contains requested value, applied value, and failure reason if unsupported.
  • Maximum payload and maximum dimensions are hard-coded defensively on both sides.
  • No frame waits indefinitely. Cancellation must interrupt socket reads, decoder waits, and ADB child processes.
  • Protocol fixtures cover truncated headers, oversized frames, reordered sequences, duplicate configuration, and corrupt H.264.

5. User experience

First-run phone flow

  1. One-screen explanation: local USB camera, no account, no internet, OBS plugin required.
  2. Request camera permission only. Ask for microphone permission later, when the user explicitly enables audio.
  3. Run a capability scan and offer only combinations the camera and encoder can sustain.
  4. Default to rear logical camera, 1080p30, 8 Mbps, SDR, autofocus, stabilization Auto, and preview on.
  5. Start session and show a large state label, elapsed time, actual FPS, temperature warning, USB/desktop state, and Stop button.

First-run desktop/OBS flow

  1. Installer places the plugin and a diagnostic utility in platform-appropriate locations.
  2. On adding Phone Camera, the source checks OBS version, adb availability, connected devices, authorization state, and whether the phone app is listening.
  3. If the device is unauthorized, show: “Unlock the phone and approve this computer for USB debugging,” with a Retry button.
  4. If the APK is absent, link to the signed release and provide a copyable install command; automatic APK installation can come later.
  5. Once connected, show live video and expose essential camera controls in the source properties. Keep advanced codec values behind an Advanced section.

6. Phased implementation roadmap

Estimates assume one experienced developer, one S24 Ultra, and an existing Linux OBS setup. They include engineering and automated tests but not store review or extensive design work. Keep each phase independently demonstrable; do not begin polish while the previous phase’s exit criteria are failing.

Phase 0 — Feasibility, naming, and baselines

2–3 working days · no production architecture commitment

  • Confirm the reference desktop OS, OBS version/package type, USB cable capability, and Android/One UI version.
  • Record the S24 Ultra’s exposed camera IDs, physical IDs, focal lengths, stream sizes, FPS ranges, encoder profiles, and bitrate modes.
  • Run scrcpy’s camera-to-V4L2 path on Linux as a baseline and record setup time, latency, CPU, temperature, and failure behavior.
  • Build a throwaway Camera2 → MediaCodec probe at 1080p30 and 720p60; drain Annex-B output and verify it with FFmpeg.
  • Check public project/package/domain naming; choose a non-conflicting working public name.
  • Write ADR-001 (native OBS source) and ADR-002 (custom ADB protocol), including rejected options.

Exit: hardware H.264 from the S24 Ultra is valid for 30 minutes, the measured baseline is documented, and no unknown blocks a USB vertical slice.

Phase 1 — Android capture engine

4–6 working days

  • Scaffold Kotlin/Compose modules, formatting, lint, unit tests, build variants, and CI APK build.
  • Implement runtime permission flow, camera capability inventory, supported-preset model, and preview.
  • Feed Camera2 directly into a configured MediaCodec input surface and emit timestamped access units.
  • Add rear/front choice, zoom ratio, autofocus, tap-to-focus, exposure compensation, torch, mirror metadata, and rotation policy.
  • Implement foreground service behavior, notification, clean Stop, app backgrounding, and screen lock testing.
  • Expose a developer statistics overlay: requested/actual FPS, bitrate, keyframes, frame count, encoder name, and thermal status.

Exit: the APK produces decodable 1080p30 for one hour, controls apply without restarting unless technically required, and leaving the activity does not corrupt the stream.

Phase 2 — Protocol and desktop vertical slice

5–7 working days

  • Freeze protocol v0.1 header/messages and create golden fixtures plus a protocol fuzzer target.
  • Implement the Android loopback server, handshake, control acknowledgements, heartbeat, single-client rule, and bounded write queue.
  • Implement desktop ADB discovery/forwarding, socket client, parser, reconnect state machine, and structured statistics.
  • Build phonecam-cli list/probe/receive/doctor and decode through libavcodec to a test renderer or null sink.
  • Test unauthorized, offline, multiple-device, app-not-running, cable-pull, truncated stream, and codec-reset cases.
  • Measure true end-to-end latency and tune encoder/keyframe/socket buffering before OBS integration.

Exit: one command produces live S24 video on the desktop, reconnects after cable removal, passes malformed-input tests, and meets a provisional median latency target of 150 ms or better.

Phase 3 — Linux OBS plugin alpha

7–10 working days

  • Scaffold the plugin with the supported OBS/CMake toolchain and pin the OBS compatibility range.
  • Register the source, publish decoded frames with correct color metadata, and implement source lifecycle/cancellation safely.
  • Add device and preset properties, live status, camera controls, mirror/rotation, low-latency buffering, and reconnect behavior.
  • Validate scene switches, hide/show, duplicate sources, source deletion, OBS shutdown, recording, and simultaneous streaming.
  • Create a local Linux installer/archive and uninstaller that never overwrites unrelated OBS files.
  • Test OBS packages likely used by contributors: native distro package first; document Flatpak sandbox limitations separately.

Exit: a clean Linux machine can install the plugin, add Phone Camera, record a 60-minute 1080p30 session, and recover from a cable disconnect without restarting OBS.

Phase 4 — Reliability, UX, and audio

5–8 working days · audio can slip to 0.2 if schedule is tight

  • Run two-hour soak, thermal, low-battery, lock-screen, app-switch, and repeated reconnect tests.
  • Add one-click support bundle, log redaction, status placeholder frames, compatibility reporting, and troubleshooting copy.
  • Add microphone capture with AudioRecord, encode AAC-LC initially, timestamp from the same monotonic clock, and send as a distinct stream ID.
  • Decode/resample audio for OBS, implement jitter correction, and validate lip-sync drift over two hours.
  • Add a user-controlled latency buffer and audio offset; default to the smallest stable buffer.
  • Complete accessibility pass: TalkBack labels, scalable text, color-independent states, and keyboard navigation in desktop properties.

Exit: all beta acceptance gates pass on the S24 Ultra, error states are actionable, and audio is either demonstrably synchronized or explicitly excluded from beta.

Phase 5 — Public beta and community foundation

4–6 working days

  • Finalize license choice and dependency/license inventory; add required notices and source headers.
  • Write setup, building, architecture, privacy, troubleshooting, contributing, security, and release documentation.
  • Publish signed APK/plugin archives, SHA-256 checksums, SBOMs, and reproducible release notes from CI.
  • Create issue forms that collect OS, OBS package/version, Android model/version, selected preset, and redacted support bundle.
  • Recruit a small device matrix: one Samsung flagship, one Pixel, and one mid-range Android device before calling the beta general-purpose.
  • Publish known limitations prominently: USB debugging requirement, Linux-first desktop support, SDR/H.264 limits, and OEM camera differences.

Exit: version 0.1.0 can be built from source, installed from signed artifacts, supported through documented diagnostics, and contributed to without private knowledge.

7. Test and measurement strategy

Automated layers

Android unit/instrumentation

  • Capability-to-preset selection and fallback.
  • Camera/encoder state machine and cancellation.
  • Protocol encode/decode, timestamps, and queue bounds.
  • Permission denial/regrant and foreground-service lifecycle.
  • Fake encoded source for deterministic transport tests.

Desktop/core

  • Parser unit tests plus fuzzing with a strict memory limit.
  • Golden H.264 configuration/keyframe/dependent-frame sequences.
  • Fake ADB process outputs for offline, unauthorized, and multi-device states.
  • Reconnect/cancellation race tests under sanitizers.
  • Color conversion and timestamp monotonicity tests.

CI gates

  • Every change: formatting, Kotlin lint/static analysis, Android unit tests, native build, native tests, sanitizer job, protocol compatibility tests, and dependency/license scan.
  • Pull requests that change protocol fixtures must identify compatibility impact and update the specification.
  • Nightly: fuzz corpus, debug Android APK, OBS plugin build, and an artifact install smoke test in a clean container/VM where practical.
  • Release tag: signed artifacts, checksums, SBOM, source archive, reproducibility metadata, and a manual S24 Ultra acceptance checklist.
  • No release is promoted because CI is green alone; physical camera, USB, OBS, latency, and soak evidence are mandatory.

8. Open-source and release strategy

License recommendation

Use GPL-2.0-or-later provisionally for original code because the deliverable includes a plugin linked to GPL-licensed OBS Studio. Before publishing, have a maintainer perform a dependency-by-dependency compatibility review and confirm the exact SPDX expression. Keep third-party code in clearly marked locations with original notices. If scrcpy code is incorporated rather than merely studied, document the Apache-2.0 origin and confirm how the combined distribution is licensed; a clean implementation is simpler for the first release. This paragraph is engineering guidance, not legal advice.

Repository essentials before the first public tag

  • LICENSE, NOTICE, machine-readable dependency inventory, and SPDX headers/policy.
  • README.md with a 60-second value proposition, honest platform status, screenshots, setup, privacy promise, and comparison to alternatives.
  • CONTRIBUTING.md, development environment bootstrap, architecture overview, protocol contribution rules, and test expectations.
  • CODE_OF_CONDUCT.md, SECURITY.md with private reporting contact, support policy, and release signing documentation.
  • Issue forms for bug, device compatibility, feature request, and security redirect; pull request template with test and license checks.
  • Developer Certificate of Origin sign-off rather than a custom CLA unless project governance later requires one.
  • Public roadmap labels: good first issue, device compatibility, protocol, OBS, Android, and platform labels.

Privacy and security promises

  • No account, ads, analytics, cloud backend, or required internet access.
  • USB mode binds only to loopback on both devices and requires an ADB-authorized computer.
  • Streaming never starts at boot or from a hidden background state; the phone displays a persistent notification while the camera is active.
  • No automatic capture files. Diagnostic recording is explicit, visibly active, and saved where the user chooses.
  • Logs redact device serials and exclude frame contents. Support bundles are created locally and reviewed by the user before sharing.
  • Protocol parser treats phone input as untrusted: fixed bounds, integer overflow checks, timeouts, fuzzing, and no shell interpolation of device-provided text.
  • Release artifacts are signed and accompanied by checksums and SBOMs; CI permissions use least privilege.

HDR/4K color or performance failures High / medium SDR 8-bit MVP. Add HDR only after capture, encoder, decoder, OBS color space, and recording output are validated end to end.

Stop/reframe criterion: if the phase-0 scrcpy baseline already gives the target users an equally good OBS experience and the proposed native source cannot materially reduce setup or improve controls/reliability, reframe the project as an OBS integration for scrcpy instead of duplicating its camera transport stack.

First development checkpoint

The first meaningful demo is not a polished phone UI. It is: S24 Ultra Camera2 → hardware H.264 → ADB-forwarded socket → desktop CLI decode, with measured latency and a cable-pull recovery. Achieve that before committing to installers, advanced controls, audio, or cross-platform work.

11. Primary references

These sources support the main technical choices. Re-check version-specific requirements when implementation begins because Android and OBS tooling evolve.

  • Android Debug Bridge documentation — USB debugging, device authorization, device selection, and host-to-device port forwarding.
  • Android MediaCodec reference — hardware codec pipeline and efficient encoder input surfaces.
  • Camera2 capture sessions and requests — configuring repeating camera output to one or more surfaces.
  • CameraCharacteristics reference — capability discovery, logical/physical cameras, sizes, FPS, and control ranges.
  • CaptureRequest reference — FPS, autofocus, exposure, stabilization, and other camera controls.
  • Android foreground service types — current camera/microphone service declarations and while-in-use restrictions.
  • Android HDR video capture — why HDR needs an end-to-end capability-specific path and should be deferred.
  • OBS plugin documentation — plugin modules and source implementation entry points.
  • Official OBS plugin template — supported CMake/build environments and release workflow starting point.
  • OBS Media Source documentation — useful fallback path and its cross-platform availability.
  • scrcpy official repository — current camera streaming, USB/ADB, V4L2 capability, performance baseline, and Apache-2.0 license.
  • v4l2loopback official repository — optional Linux system-wide virtual camera path and GPL licensing.
  • OBS Studio license and OBS plugin template license — inputs to the pre-release compatibility review.
