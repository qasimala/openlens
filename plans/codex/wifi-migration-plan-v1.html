OpenLens Wi-Fi migration Plan v1 2026-08-10 For independent review

OpenLens without ADB

A detailed implementation plan for secure local Wi-Fi discovery, one-time pairing, encrypted camera transport, and automatic reconnection between the Android and Linux desktop apps.

Target experience: on first use, open both apps and confirm a matching six-digit pairing code once. On later uses, connect both devices to the same local network, open both apps, and click Start camera on the PC. No ADB, USB debugging, cable, IP address, account, cloud service, or per-session phone approval is required.

Repository: /home/qasim/Dev/openlens
Existing baseline: Android Camera2/MediaCodec app, binary protocol, C++/Qt desktop app, FFmpeg decoder, V4L2 sink and native OBS source.
Primary reference: Samsung Galaxy S24 Ultra and CachyOS Linux.

2. User experience

2.1 First use

  1. Install OpenLens on Android and OpenLens Desktop on Linux.
  2. Connect both devices to the same trusted Wi-Fi network.
  3. Open the Android app. Grant the standard Camera permission and, when required by the Android version, Local network/Nearby devices permission.
  4. The phone displays Ready to pair and advertises itself as an OpenLens camera.
  5. Open the desktop app. It discovers the phone and presents Pair this phone.
  6. Both devices display the same six-digit code derived from the two TLS identities. The user confirms that the codes match on both devices.
  7. Each device pins the other device's certificate fingerprint. Pairing mode closes immediately.
  8. The desktop shows Paired · Ready. The user clicks Start camera.

2.2 Every later use

  1. Open OpenLens on the phone and computer while on the same network.
  2. The desktop automatically discovers the previously paired phone by stable random device ID and validates its pinned TLS certificate.
  3. Click Start camera. Streaming begins with no code and no phone confirmation.
  4. Use OpenLens in OBS. Camera settings and Stop remain controlled from the desktop; emergency Stop remains available on the phone.

2.3 Multiple phones or computers

  • The desktop lists every discovered OpenLens phone but automatically selects the last paired phone when unambiguous.
  • The phone displays paired computers by friendly name and last-seen time.
  • Adding another computer requires an explicit Pair new computer action on the phone.
  • Only one computer may own the camera session at a time. Additional authenticated clients receive a structured BUSY response.
  • Either side can forget/revoke a pairing. Revocation is immediate for new sessions.

3. Scope and non-goals

In scope for Wi-Fi v1

  • Android NSD advertisement.
  • Linux Avahi discovery.
  • TLS 1.3 encryption.
  • One-time mutual pairing and certificate pinning.
  • Existing H.264 video/control protocol over TLS.
  • Automatic rediscovery and bounded reconnect.
  • Qt and Android pairing/connection UI.
  • V4L2 and native OBS output.

Explicitly out of scope

  • Internet relay, remote access or cloud signaling.
  • TURN/STUN/WebRTC for cross-network use.
  • Unauthenticated LAN camera access.
  • iOS support.
  • Audio capture.
  • Background boot-time advertising.
  • Automatic router configuration.
  • Public release/signing decisions.

5. Security and pairing design

Wi-Fi changes the trust boundary. ADB previously inherited Android's USB-debugging authorization. The Wi-Fi design must replace that trust with encrypted transport, mutual device identity, explicit one-time pairing and revocation. Merely checking “same subnet” is not authentication.

5.1 Persistent identities

  • Phone: generate a persistent EC P-256 signing key in Android Keystore with a self-signed X.509 certificate. The private key is non-exportable. Use a stable random UUID as the OpenLens device ID; do not use IMEI, Android ID, Wi-Fi MAC or serial number.
  • Desktop: generate a persistent EC P-256 key and self-signed X.509 certificate with OpenSSL. Store the private key in an OpenLens-owned configuration directory with mode 0600; write atomically.
  • Certificates are identities, not public-CA web certificates. Trust is created only by the pairing ceremony and SHA-256 certificate pins.
  • Identity reset must be explicit and warn that all pairings will be invalidated.

5.2 First-pair ceremony

  1. The phone enters pairing mode only while its pairing screen is visible. Pairing mode expires after two minutes.
  2. The desktop creates a TLS 1.3 connection using its self-signed client certificate. During this explicit pairing connection only, both sides temporarily accept an unpinned self-signed peer certificate after validating certificate structure, supported key type and proof of private-key possession in TLS.
  3. Both sides calculate certificate fingerprints: Fphone = SHA-256(phone DER certificate) and Fdesktop = SHA-256(desktop DER certificate).
  4. Both calculate the same SAS from a domain-separated hash of the two ordered fingerprints: SAS = TruncateDecimal(SHA-256("OpenLens Pairing v1" || min(Fphone,Fdesktop) || max(Fphone,Fdesktop)), 6).
  5. The same zero-padded six-digit code is shown on both screens along with the peer-friendly name.
  6. The user confirms Codes match on both devices. A mismatch cancels pairing and closes the TLS connection.
  7. Only after both confirmations are exchanged over the active TLS channel does each side atomically store the peer device ID, certificate pin and friendly name.
  8. The pairing connection closes. The normal session reconnects using strict pin validation.

Security rationale: an active relay that terminates two TLS connections presents different peer certificates to each endpoint, producing different codes. A transparent relay leaves the TLS channel end-to-end and gains no plaintext. Confirmation on both devices prevents an unattended LAN client from enrolling itself.

5.3 Normal authenticated sessions

  • TLS 1.3 only; no plaintext fallback and no “accept all certificates” path outside explicit pairing mode.
  • Both peers present certificates. Trust managers verify the exact pinned SHA-256 DER fingerprint for the selected device ID.
  • Certificate/device-ID mismatch is a hard failure with actionable UI: Identity changed — pairing required.
  • Application messages begin only after TLS completes. Existing protocol magic is retained inside TLS for framing and defensive parsing.
  • Disable TLS compression, renegotiation and legacy protocol versions. Use platform/OpenSSL AEAD cipher negotiation.
  • Limit one active camera controller. Pairing sockets, authenticated idle sockets and streaming sockets have separate timeouts.

5.4 Pairing abuse controls

  • Pairing advertisement appears only while the phone's pairing UI is visible.
  • One active pairing attempt at a time; maximum five failed attempts per pairing window.
  • All unconfirmed attempts expire and leave no trust record.
  • No pairing material, codes, full certificate data or video content in normal logs.
  • Phone and desktop expose Forget and Forget all actions with confirmation.
  • Paired device count is capped (initially 10) to prevent unbounded storage.

6. Local discovery design

6.1 DNS-SD contract

Service type: _openlens._tcp.. The phone chooses an ephemeral TCP port and registers through Android NsdManager. The Linux desktop browses/resolves through libavahi-client.

TXT keyExampleRules
v2Protocol major version; required.
id6e675…Random stable OpenLens device UUID, encoded without personal identifiers.
nameQasim's PhoneUser-editable friendly name, length-limited and escaped.
tls1Required; clients reject missing/false.
pair0 or 1Whether the phone is currently accepting a new pairing.
busy0 or 1Informational only; authenticated server response is authoritative.
  • Do not advertise IP addresses, certificate fingerprints, pairing codes, model/serial identifiers or capabilities in TXT records.
  • Resolve both IPv4 and IPv6. Prefer reachable addresses on the interface Avahi resolved; use Happy Eyeballs-style bounded attempts rather than concatenated long timeouts.
  • Service loss updates UI immediately but does not alone terminate an already connected TLS socket.
  • Duplicate names are normal; stable device ID and certificate pin determine identity.

Android's official NSD API implements DNS-based service discovery. Current target SDK 36 can use LAN sockets with INTERNET; Android 17/target SDK 37 introduces mandatory local-network permission or system-mediated discovery grants. See the official NSD guide and local-network permission guidance.

7.2 Service lifecycle

  1. While MainActivity is visible, a bound service/controller may advertise and accept TLS connections without keeping the camera open.
  2. After an authenticated desktop sends START/CONFIGURE while the activity is foreground, promote CameraStreamingService to a foreground service declared as camera|connectedDevice, then open Camera2 and MediaCodec.
  3. Use the current ongoing notification, camera privacy indicator and Stop action throughout capture.
  4. When streaming ends, close camera/encoder/socket, remove the camera foreground state, and resume ready advertisement only if the app is still intentionally available.
  5. If the Android task is dismissed while not streaming, stop advertising. If dismissed while streaming, use the user's configured “continue while backgrounded” policy; default for v1 is continue until desktop Stop, phone notification Stop, socket loss timeout or process termination.

Foreground-service declarations must follow Android's current camera and connected-device rules: camera access requires the camera type and permission, while connected-device work requires its declared type/permission and a qualifying network permission. See the official foreground-service type documentation.

7.3 Manifest and permission changes

  • Add android.permission.INTERNET.
  • Add android.permission.FOREGROUND_SERVICE_CONNECTED_DEVICE.
  • Add the minimal qualifying network permission required for connected-device FGS, expected to be CHANGE_NETWORK_STATE; do not request location.
  • Declare service type camera|connectedDevice.
  • Keep CAMERA, FOREGROUND_SERVICE and FOREGROUND_SERVICE_CAMERA.
  • For target SDK 36, do not prematurely request the Android 17 ACCESS_LOCAL_NETWORK permission. Add a versioned permission adapter and test Android 16's opt-in restriction mode. When targeting SDK 37, declare/request Local network or adopt the system picker path.

7.4 Android UI

  • Offline: “Connect this phone to Wi-Fi.”
  • Ready: phone name, network name if safely available, “Waiting for paired computer,” and paired-device management.
  • Pairing: large six-digit SAS, requesting computer name, countdown and Match/Cancel actions.
  • Streaming: preview, connected computer, resolution/fps/bitrate/frame stats, camera indicator explanation and Stop.
  • Error: actionable network/TLS/permission message, retry and diagnostics copy button.
  • Rotation must continue to preserve the camera surface and network session.

8. Linux desktop implementation design

8.1 Core additions

  • Link avahi-client/avahi-common for DNS-SD browsing and resolution.
  • Link OpenSSL 3 for TLS 1.3, X.509 identity generation/loading, peer-certificate extraction and pinned verification.
  • Add WifiDiscovery, DesktopIdentityStore, TlsClientTransport and pairing state-machine classes.
  • Refactor OpenLensSession so ADB forward/launch is one transport provider rather than hard-coded session setup.
  • Preserve the existing protocol parser, decoder, frame transforms, V4L2 sink and OBS integration above the transport boundary.

8.2 Desktop GUI changes

  • Replace ADB/USB readiness cards with Wi-Fi, Phone discovery, Pairing, Virtual camera and OBS integration.
  • Device picker shows friendly name, paired/unpaired state, availability and last seen; never exposes certificates or raw IPs in the normal UI.
  • Pairing dialog displays a large six-digit code and requires Codes match confirmation. Cancellation leaves no partial record.
  • Remember the last paired phone. If exactly one paired phone is available, select it automatically.
  • Start remains disabled until a pinned phone is reachable and /dev/video42 or the selected native OBS path is ready.
  • During streaming, allow safe live controls (zoom, exposure and torch) to update immediately; camera/preset changes may perform a controlled stream reconfiguration.
  • Add Forget phone, Pair another phone and Network diagnostics.

9. Protocol v2 changes

9.1 Preserve the proven media framing

Keep the existing fixed header, maximum payload enforcement, incremental parsing, video config/frame messages, stats, controls, ping/pong, error and end-stream semantics. TLS supplies confidentiality and integrity; the OpenLens framing still supplies message boundaries, versioning and defensive validation.

9.2 Add connection-stage messages

MessageDirectionPurpose
PAIR_REQUESTDesktop → phoneFriendly name, random device ID, certificate hash, protocol range.
PAIR_CHALLENGEPhone → desktopPairing attempt ID, phone identity metadata and expiry; no secret code transmitted.
PAIR_CONFIRMBoth directionsConfirms the locally displayed SAS matched. Bound to attempt ID and peer pins.
PAIR_RESULTBoth directionsAtomic success/failure and stable peer record identifiers.
AUTHENTICATED_HELLOBoth directionsNormal-session identity, supported protocol range and feature bits after strict mTLS.
START_STREAMDesktop → phoneExplicitly authorizes camera activation and carries initial configuration.
BUSYPhone → desktopAnother paired controller owns the camera; includes no identifying data about that controller.

9.3 Version and limit rules

  • Increment protocol major to 2 for Wi-Fi/pairing semantics; retain explicit v1 ADB compatibility only inside the fallback provider.
  • Reject unknown required messages, invalid state transitions and metadata above the existing bounded limit.
  • Pairing messages are legal only on a pairing-mode TLS socket. Camera messages are illegal until strict authenticated hello and START succeed.
  • All timeouts and limits become named constants with unit tests: discovery resolve, TLS handshake, pairing confirmation, idle authenticated client, frame liveness and reconnect window.
  • Add cross-language fixtures for every new message and state-transition failure.

10. Connection, stream and recovery lifecycle

10.1 Phone state machine

STOPPED
  └─ app visible → ADVERTISING
       ├─ unpaired client + pairing UI → PAIRING
       │    ├─ both confirm → ADVERTISING (paired)
       │    └─ cancel/timeout/mismatch → ADVERTISING
       ├─ pinned client TLS → AUTHENTICATED_IDLE
       │    ├─ START_STREAM → STARTING_CAMERA → STREAMING
       │    ├─ idle timeout → ADVERTISING
       │    └─ identity mismatch → REJECTED
       └─ app closes while idle → STOPPED

STREAMING
  ├─ network interruption → RECONNECT_GRACE
  ├─ desktop END_STREAM → ADVERTISING or STOPPED
  ├─ phone Stop → ADVERTISING or STOPPED
  └─ fatal camera/encoder error → ERROR → ADVERTISING

10.2 Reconnection policy

  • On Wi-Fi loss, immediately stop writing, preserve the selected phone identity and show a disconnect slate in OBS.
  • Rediscover the same stable device ID for up to 60 seconds with capped exponential backoff and jitter.
  • Require the same pinned certificate after rediscovery. Never silently pair a replacement device with the same friendly name.
  • After reconnect, perform a fresh TLS handshake and protocol hello/configure. Request an encoder keyframe.
  • Do not queue unbounded video during a network outage. The phone uses a small latest-frame-biased encoded queue and reports drops.
  • If the phone changes Wi-Fi networks, discovery and reconnect may recover if both devices again share a reachable LAN; otherwise fail clearly after the bounded window.

11. Migration from the current ADB architecture

  1. Extract transport interfaces first. Make existing ADB tests pass unchanged through an AdbTransportProvider. This proves the refactor did not alter media behavior.
  2. Add Wi-Fi discovery/TLS beside ADB. The developer CLI chooses transport explicitly. The GUI remains on ADB until Wi-Fi pairing and live-stream gates pass.
  3. Make Wi-Fi the GUI default. Remove USB-debugging and ADB readiness requirements from normal UI. Keep a developer fallback setting hidden behind an environment/build option.
  4. Update OBS integration. Both V4L2-driven desktop GUI and native OBS source use the same paired-device discovery and TLS session layer.
  5. Remove ADB from user documentation and packaged runtime requirements. Do this only after clean-machine validation proves normal operation without Platform Tools installed.
  6. Decide final fallback policy. Before public beta, either retain an explicitly unsupported developer ADB mode or delete it and its dependencies. Do not expose two confusing primary workflows.
Compatibility rule: do not overload the existing ADB socket name or v1 handshake to guess transport mode. Providers and protocol major versions must be explicit so errors are diagnosable.

12. Implementation phases

Phase 0 — Feasibility spikes and ADR

Goal: prove the risky platform assumptions before restructuring production code.

  • Android NSD advertiser visible from avahi-browse on the reference LAN.
  • Android TLS 1.3 server using an Android Keystore self-signed EC certificate.
  • OpenSSL client certificate presentation and extraction on Android.
  • Deterministic matching SAS on Android and C++ from the same two DER certificates.
  • Sustained encrypted TCP throughput above 25 Mbps for 15 minutes with no corruption.
  • Validate camera foreground-service promotion from an app-visible authenticated request.

Exit: ADR records go/reframe decisions, measured throughput, lifecycle behavior and exact dependencies. No production migration before these pass.

Phase 1 — Transport-neutral core

  • Introduce transport interfaces on Kotlin and C++ sides.
  • Move framing/session runner away from LocalSocket and raw POSIX socket setup.
  • Implement adapters for the existing ADB path.
  • Preserve all current protocol/core/Camera2/MediaCodec tests and the live USB path.

Exit: no user-visible change; ADB still works through abstractions with equal live stats.

Phase 2 — Identity, TLS and pairing

  • Implement Android Keystore and desktop OpenSSL identity stores.
  • Implement pairing-only permissive certificate capture, SAS, two-sided confirmation and strict post-pair pinning.
  • Add revoke/reset flows and storage permission checks.
  • Add unit/integration tests for order-independent SAS, mismatch, MITM simulation, timeout, cancellation, pin change and atomic persistence.

Exit: loopback and two-process tests prove encrypted mutually pinned connections; no camera yet.

Phase 3 — Android NSD host and phone UI

  • Implement service registration, TLS accept loop, foreground lifecycle and Compose state screens.
  • Add permissions and Android 16 restricted-local-network compatibility testing.
  • Pair the real S24 with a desktop diagnostic client.

Exit: phone can advertise, pair, authenticate, revoke and survive rotation/network changes without Camera2.

Phase 4 — Linux discovery and desktop pairing UI

  • Implement Avahi browser/resolver and device model.
  • Add Qt device discovery, code confirmation, paired/available states and forget actions.
  • Add CLI Wi-Fi discovery/pair/forget JSON commands.

Exit: clean first-pair and subsequent auto-recognition work without ADB installed.

Phase 5 — Camera stream over Wi-Fi

  • Move the proven HELLO/CAPABILITIES/CONFIGURE/CONTROL/video loop onto strict mTLS transport.
  • Promote the Android service only when authenticated Start activates Camera2.
  • Support stop, errors, stats, keyframes, bounded queues and single-controller BUSY.
  • Verify desktop preview, /dev/video42 and native OBS output.

Exit: the target user journey works end to end over Wi-Fi with Platform Tools absent.

Phase 6 — Recovery, controls and performance

  • Implement mDNS rediscovery and strict-pin reconnect.
  • Make safe desktop controls live during streaming.
  • Measure startup, bandwidth, latency, loss and thermal behavior at 1080p30/720p30.
  • Improve keyframe/rebuffer behavior without hiding disconnections.

Exit: reconnection and performance gates pass on the reference system.

Phase 7 — Packaging, documentation and hardening

  • Make Wi-Fi default, remove ADB from user dependencies, refresh installers/bundle/SBOM/licenses.
  • Add CI for OpenSSL/Avahi builds and TLS/pairing tests.
  • Run security review, fuzzing, long soaks, network captures and clean-machine installation.
  • Update privacy policy, threat model, troubleshooting and release evidence.

Exit: beta candidate only after every mandatory gate is evidenced.

13.2 Physical reference-system gates

  1. Clean phone/desktop pair using matching code; mismatch is rejected.
  2. Second use discovers and authenticates automatically without code.
  3. Unpaired LAN client cannot start, control or receive camera data.
  4. Changed desktop certificate is rejected until explicitly re-paired.
  5. ADB and Android Platform Tools are absent; normal GUI still works.
  6. 1080p30 streams for 60 minutes with retained frame/drop/network/thermal metrics.
  7. Two-hour OBS recording through V4L2 and separate native-plugin soak.
  8. Ten portrait/landscape rotations do not stop transport or camera.
  9. Twenty Wi-Fi disruptions/reconnects meet the ≤10-second target when reachable.
  10. Fifty Start/Stop cycles release camera, service, socket and OBS/V4L2 ownership every time.
  11. Router client isolation produces a clear “phone discovered but unreachable” or “not found” diagnosis.
  12. Traffic capture confirms all OpenLens session payloads are encrypted and no internet endpoints are contacted.
  13. Locked/background behavior matches documented policy and never bypasses Android security UI.

13.3 Security review gates

  • Independent review of permissive pairing trust manager proves it is unreachable outside an active pairing window.
  • Independent MITM test confirms endpoint codes differ when TLS is terminated by a relay.
  • Certificate private keys never appear in logs, bundles, backups or support reports.
  • Peer pin comparison is constant-time where practical and never falls back to hostname/public CA trust.
  • Pairing database and desktop private key permissions are verified on disk.
  • Denial-of-service controls prevent unbounded threads, sockets, metadata or encoded-frame queues.

16. Claude review checklist

The reviewing agent should challenge the plan specifically on these points:

  1. Does the two-certificate SAS plus dual confirmation correctly prevent an active TLS-terminating MITM during first pairing?
  2. Can Android's TLS server reliably use a self-signed EC certificate/private key held in Android Keystore on API 31–36?
  3. Is mutual TLS with a permissive pairing-only trust manager cleanly separable from strict pinned normal sessions?
  4. Is camera|connectedDevice the correct foreground-service declaration and is CHANGE_NETWORK_STATE the least-privileged qualifying permission?
  5. Can the app advertise/accept while visible without an unnecessary persistent foreground service, then safely promote when capture starts?
  6. Is Avahi the right Linux dependency for target distributions, and are interface/scope handling and daemon absence addressed?
  7. Should manual IP entry exist as a diagnostic fallback, and how can it remain pin-safe?
  8. Are protocol v2 pairing states replay-safe, bounded and impossible on normal streaming sockets?
  9. Is keeping ADB as a temporary fallback worth the maintenance/security surface?
  10. Are startup latency, throughput, reconnect and soak thresholds realistic for 1080p30 on the S24 Ultra?
  11. Which portions require a formal threat model or external cryptographic review before implementation?
  12. Are any current Android 17 local-network permission assumptions likely to change the chosen discovery path?

Requested reviewer output
