Review — Wi-Fi Migration Plan v1

Claude's independent review of plans/codex/wifi-migration-plan-v1.html, in the format requested by its §16. Section references (§n) point at the plan under review.

0.Verdict

Architecture: sound and well-scoped. mDNS discovery + TLS 1.3 + one-time mutual pairing + certificate pinning + PC-owned sessions is the correct design for LAN camera control, and the plan is admirably security-conscious (explicit trust-boundary framing, revocation, pairing-window capability isolation, bounded queues, no cloud). The layering (transport-neutral core, ADB as a transitional provider) is the right migration strategy.
One critical cryptographic flaw blocks the pairing design as written (§5.2): the six-digit SAS is a truncated hash of two attacker-choosable certificates with no fresh nonces or commitment. An active MITM can grind its own certificates to force both endpoints to display the same code, defeating the entire pairing guarantee. This is fixable with a standard commitment-based numeric-comparison construction (§1 below). Do not implement pairing (Phase 2) until this is redesigned. Everything upstream and downstream of the ceremony is fine.

1.Critical security blocker — the SAS is grindable

The flaw

§5.2 defines SAS = TruncateDecimal(SHA-256("OpenLens Pairing v1" || min(Fp,Fd) || max(Fp,Fd)), 6), where Fp, Fd are SHA-256 fingerprints of the phone/desktop certificates, computed after a TLS handshake that "temporarily accepts an unpinned self-signed peer certificate." The rationale (§5.2, footnote) is: a relay that terminates two TLS connections shows different certs to each side → different codes → user sees a mismatch.

That rationale holds only for a passive or naïve relay. The attacker generates its own EC keypairs and therefore chooses the certificates it presents. In a MITM relay:

Phone sees attacker cert A_p  → computes  SAS_phone   = H(sort(P,   A_p))
Desktop sees attacker cert A_d → computes  SAS_desktop = H(sort(D,   A_d))
Attacker knows P and D (it terminated both handshakes) and freely picks A_p, A_d.
Goal: make SAS_phone == SAS_desktop so BOTH users see matching codes and confirm.

Six decimal digits ≈ 219.9 of entropy. The attacker fixes any A_d (giving target T = H(sort(D,A_d))), then grinds fresh A_p until H(sort(P,A_p)) == T — about 106 cheap EC keygen+hash operations, i.e. well under a second. (Birthday framing: ~103 candidates on each side also suffices.) The attacker genuinely possesses every private key it generates, so TLS proof-of-possession is passed and adds no protection. Both endpoints then pin the attacker's certs — a total, silent break.

The §13.3 test "codes differ when TLS is terminated by a relay" would pass against a naïve relay and give false confidence; it does not model a grinding attacker.

The fix — commitment-based numeric comparison with fresh nonces

Truncated fingerprint comparison is only safe when the compared value is full-length (≥128 bits) or when short codes are made ungrindable by a commit-before-reveal exchange of fresh random nonces — the construction used by ZRTP SAS and Bluetooth/CTAP numeric comparison. Concretely:

1. Phone picks nonce_p (≥128-bit random). Desktop picks nonce_d.
2. Phone sends commit = H("OpenLens Pair v1 commit" || nonce_p)   // BEFORE seeing nonce_d
3. Desktop sends nonce_d.
4. Phone reveals nonce_p. Desktop verifies commit == H(... || nonce_p).  // abort on mismatch
5. Both compute, over the ACTUAL pinned certs (channel binding) + both nonces:
   SAS = TruncateDecimal(
           H("OpenLens Pair v1 sas" || nonce_p || nonce_d || Fp || Fd), 6)
6. User compares the 6 digits on both screens and confirms on both. Then pin.

Because the phone commits to nonce_p before learning nonce_d (and vice-versa for the freshness of nonce_d), neither the attacker nor a party can search for colliding SAS values after the fact — the inputs are locked before they are known. This makes a 6-digit code safe (attacker success ≈ 1-in-106 per attempt, and §5.4's "max 5 attempts per window" caps it). Bind the SAS to the certs (Fp,Fd) so the confirmed code authenticates the exact keys being pinned. Consider using the TLS exporter (RFC 5705) as the channel-binding input instead of, or in addition to, the cert fingerprints for defence in depth.

Alternative if you prefer typing over comparing: a PAKE (CPace / SPAKE2) seeded by a code one side generates and the user types into the other. It's stronger but changes the compare-not-type UX the plan wants; commitment-based numeric comparison is the better match here.

Also: §16 asks for a formal review of exactly this. Adopt a published construction and get the crypto independently reviewed rather than shipping a bespoke SAS. This is the one part of the project that genuinely warrants it.

2.Medium issues (revise before the relevant phase)

2.1 The ADB fallback carries a known critical vulnerability (§3 "USB/ADB", §11, §16 Q9)

The current ADB transport uses an abstract-namespace LocalServerSocket whose session name arrives via an exported="true" activity intent, with no socket authentication — a zero-permission app on the phone can start a session with its own name and receive the camera feed (flagged in the implementation review of the prior handoff). If ADB is retained "temporarily as a developer fallback," that code path must not ship in release builds — gate it behind a compile-time flag excluded from the packaged APK, not merely a hidden runtime setting. Cleanest is to delete it before public beta (the plan already schedules this decision in §11 step 6; bring it forward and make "release build contains no ADB transport" a hard gate). Recommendation: keep ADB dev-only and compiled-out of release; do not maintain two supported workflows.

2.2 Foreground-service type may be over-declared (§7.2–7.3, §16 Q4)

The camera FGS type (with FOREGROUND_SERVICE_CAMERA) is required and is what actually gates camera access while backgrounded. Holding a TCP socket is not itself a restricted FGS behavior, so connectedDevice is likely unnecessary — the camera FGS keeps the process (and its socket) alive during streaming. Adding connectedDevice pulls in FOREGROUND_SERVICE_CONNECTED_DEVICE + a qualifying permission for a type whose intent is companion/BT/USB devices, not LAN sockets. CHANGE_NETWORK_STATE does qualify if you keep it, and is a reasonable least-privilege choice — but first verify on-device that camera alone sustains a backgrounded stream (it should). Drop connectedDevice unless a concrete test shows it's needed. Advertising/accepting while only ready (not streaming) correctly needs no FGS at all (§16 Q5 — agreed, this is right).

2.3 No measured latency baseline to regress against (§10.3, §16 Q10)

The targets (1080p30@8Mbps, ≤100 ms queue budget, start-to-frame ≤2 s) are realistic for LAN Wi-Fi 5/6. But the ADB path's glass-to-OBS latency was never measured (it was a NOT-RUN gate in the prior release ledger), so there is no baseline to prove Wi-Fi doesn't regress it — and Wi-Fi adds jitter USB didn't. Establish the glass-to-glass latency baseline now (the LED/high-fps-camera method) so Phase 6 has a number to beat. The bounded latest-frame-biased queue (§10.2) is the correct jitter mitigation; keep it strict and instrument drops.

2.4 Certificate expiry vs. pin lifetime is unspecified (§5.1, §13.1)

§13.1 lists "expired/invalid cert handling," but for a pin-based identity, trust derives from the key, not X.509 validity. If self-signed identities carry a short NotAfter and sessions reject on expiry, every pairing silently dies at that date. Decide explicitly: either issue very long-lived (or effectively non-expiring) identity certs, or ignore NotAfter for pinned peers and treat the pinned SPKI/cert hash as the sole trust anchor. State this in the protocol v2 spec so Android and desktop agree.

3.Minor / privacy notes

  • TXT name broadcasts a personal string (§6.1, "Qasim's Phone") to everyone on the LAN. Default to a non-personal name (e.g. "OpenLens phone") or warn; the friendly name isn't needed for correctness (device ID + pin are).
  • Stable device UUID in TXT is a passive-tracking handle (§6.1 id) — any LAN observer can link the device across sessions/networks. Acceptable for a camera you're intentionally advertising, but note the linkability; advertising only while the app is foreground (already planned) limits exposure.
  • Constant-time SAS/pin comparison (§13.3 says "where practical") — for a 6-digit visually-compared SAS this is moot, but the 32-byte pin comparison on the hot auth path should be constant-time; make it unconditional, not "where practical."
  • Avahi absence (§16 Q6): Avahi is the right Linux dependency; handle a missing/stopped avahi-daemon with a clear diagnostic and the manual-IP fallback (below), and preserve the interface/scope ID for link-local IPv6 (already noted in §6.1 — good).
  • Manual IP fallback (§16 Q7): yes, keep it as an advanced/diagnostic entry. It stays safe because it still performs strict mTLS pinning against the stored device ID — you lose discovery, never authentication.
  • DoS on the accept loop (§5.4/§13.2): good coverage; add explicit rate-limiting of TLS handshakes and a cap on concurrent half-open connections, since anyone on the LAN can reach the port.

6.Concrete replacements proposed

  1. SAS: replace the truncated-hash-of-certs with commit-before-reveal nonce exchange, SAS bound to both cert fingerprints (and ideally the TLS exporter). §1 has the exact construction.
  2. ADB: compile-time-gated dev-only transport, excluded from release artifacts; fix or excise the abstract-socket auth gap regardless.
  3. FGS: ship camera only unless an on-device test proves connectedDevice is required.
  4. Certs: pin the key/SPKI hash and treat it as the sole trust anchor; don't let NotAfter silently kill pairings.
  5. MITM test (§13.3): upgrade it to model a grinding relay (attacker chooses its certs), not just a transparent one — the v1 SAS passes the naïve test and fails the real one.
