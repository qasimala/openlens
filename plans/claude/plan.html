1.Goals & Non-Goals

MVP definition: Plug in the S24 Ultra over USB with debugging enabled, run one desktop command, and the phone's rear camera appears as a video source in OBS at 1080p/30fps with < 150 ms latency.

Goals

  • USB-first (ADB transport): zero network setup, reliable bandwidth, charges while streaming.
  • Low latency: hardware H.264 encode on the phone, hardware decode on the PC; target < 150 ms glass-to-glass.
  • OBS as first-class consumer: via a virtual V4L2 camera on Linux (works in every app, not just OBS).
  • High quality: up to 4K30 / 1080p60 depending on encoder limits; manual controls (lens selection, torch, focus, exposure) later.
  • Fully open source — no accounts, no telemetry, no watermarks, no paywalled resolutions.

Non-Goals (for v1)

  • iOS support (architecture shouldn't preclude it, but Android ships first).
  • Wi-Fi streaming (planned for v2 — the protocol will be transport-agnostic so this is additive).
  • Audio (v2; protocol reserves a channel for it).
  • Windows/macOS virtual cameras (v2 — the desktop client core will be cross-platform, only the virtual-camera sink is OS-specific).

2.Prior Art & Why This Approach

ProjectWhat it doesTakeaway for OpenLens
scrcpy (Genymobile) Mirrors screen (and since v2.0, cameras) over ADB using a server jar pushed via adb push + app_process, H.264 over a localabstract socket. Also has --v4l2-sink. The gold-standard architecture for USB streaming. OpenLens differs by being a real installable app with a camera-centric UI (framing preview, lens/exposure controls, status), not a headless pushed server. Study its socket + codec handling closely.
DroidCam / Iriun / Camo Phone-as-webcam apps, mostly proprietary, freemium (720p caps, watermarks). Validates demand. The open-source, no-caps angle is the differentiator.
Android 14 native webcam (UVC gadget) Android 14+ can present itself as a standard USB webcam ("Use phone as webcam" in USB settings). The S24 Ultra supports this. Great baseline, but limited: no resolution/bitrate control, typically capped quality, no app-level controls. OpenLens targets higher quality + control. Document it in the README as the "no-install" alternative so users can compare.
v4l2loopback Kernel module exposing a virtual /dev/videoN device. The standard Linux virtual-camera sink; OBS (and browsers, Zoom, etc.) consume it natively. OBS's own Virtual Camera uses it too.

Chosen approach: installable Android app that runs a foreground service with an H.264 encoder, streamed over an ADB-forwarded socket to a small desktop client that decodes and writes into v4l2loopback. This is the scrcpy transport model married to a proper camera app UX.

4.Wire Protocol (v1)

Two logical channels multiplexed on one TCP stream (or two forwards — decide during prototyping; start simple with two sockets: video and control).

Handshake

[magic "OLNS"][u16 proto_version][u16 flags]
[device info JSON: model, camera list (id, facing, physical lenses, max res/fps), codec caps]

Video channel (phone → desktop)

Per packet:
[u64 pts_us][u32 size][u8 flags: KEYFRAME|CONFIG][payload: H.264 Annex-B NAL units]

- First packet after (re)configure carries SPS/PPS (CONFIG flag).
- Encoder settings: low-latency mode, repeat-SPS/PPS on keyframes,
  keyframe interval ~2 s, CBR-ish bitrate (default 12 Mbps @1080p, 30 @4K).

Control channel (desktop → phone, JSON lines)

{"cmd":"start","camera":"0","width":1920,"height":1080,"fps":30,"bitrate":12000000}
{"cmd":"switch_camera","camera":"2"}        // ultrawide / tele on S24U
{"cmd":"set","torch":true}
{"cmd":"set","zoom":2.0}
{"cmd":"set","exposure_compensation":-1}
{"cmd":"stop"}

Version every message set; the handshake's proto_version gates compatibility so app and CLI can ship independently.

5.Android App Design

Stack

  • Kotlin, minSdk 26 (Android 8) — MediaCodec surface-input and Camera2 are solid from here; realistically test 29+.
  • CameraX for the happy path (preview + VideoCapture-style Surface pipeline); drop to Camera2 interop for physical-lens selection (S24 Ultra exposes ultrawide / wide / 3x / 5x as physical cameras of a logical camera) and manual controls.
  • Foreground service with foregroundServiceType="camera" — required on Android 14 for camera use while backgrounded; persistent notification with a Stop action.
  • Jetpack Compose UI: live preview, big status indicator (Idle / Waiting for PC / Streaming), resolution+fps picker, lens switcher, torch toggle.

Pipeline detail

  1. Open camera → bind two outputs: preview SurfaceView + encoder input Surface from MediaCodec.createInputSurface().
  2. Configure MediaCodec: video/avc, requested size, BITRATE_MODE_CBR, KEY_LATENCY=0 / low-latency flag where supported, KEY_REPEAT_PREVIOUS_FRAME_AFTER to keep the stream alive on static scenes.
  3. Drain encoder on a dedicated thread → frame packets onto the LocalServerSocket.
  4. Control listener thread applies commands via CameraControl/CaptureRequest; a resolution change tears down and rebuilds the codec (send CONFIG packet again).

Android gotchas to plan for

  • Rotation: send display/sensor orientation in the handshake and on change; desktop rotates (or negotiate fixed landscape for v1).
  • Thermals: S24 Ultra will throttle on long 4K sessions — surface thermal status (PowerManager.getThermalHeadroom) in the UI and auto-step-down bitrate.
  • Samsung quirk: some Samsung devices hide physical lens IDs from third-party apps; verify what CameraManager exposes on the S24U early (Phase 0 spike).
  • Battery optimization: USB power mostly solves it, but exempt the service from doze prompts anyway.

6.Desktop Client Design (openlens-cli)

$ openlens                # detect device, adb forward, launch app activity/service,
                          # connect, decode, create/attach v4l2 device, stream
$ openlens --list-cameras # query device camera capabilities
$ openlens --res 4k --fps 30 --camera tele
$ openlens --setup        # install/load v4l2loopback with the right options (guided)
  • ADB handling: shell out to the system adb binary (simplest, most robust) — detect device, adb forward tcp:27183 localabstract:openlens, adb shell am start-foreground-service …. Nice error messages for "no device", "unauthorized", "multiple devices".
  • Decode: libavcodec; try VAAPI hw decode, fall back to software (1080p30 software decode is trivial on any desktop CPU).
  • v4l2 sink: open /dev/videoN, set format (I420, WxH, fps), write frames. Auto-detect an existing v4l2loopback device labeled "OpenLens"; offer --setup to create it (needs sudo — print the exact commands instead of silently escalating).
  • Resilience: auto-reconnect on cable blips; hold last frame or show a "reconnecting" slate in the virtual cam so OBS doesn't lose the source.
  • Stats: --stats overlay to stderr: fps, bitrate, decode latency, dropped frames.

7.OBS Integration

  • v1: OBS → Sources → Video Capture Device (V4L2) → select "OpenLens". Zero OBS-side code. Document with screenshots.
  • v2 (optional): native OBS plugin (obs-openlens) that connects to the phone directly and hands decoded frames to OBS — skips the loopback device, enables per-source settings UI inside OBS, and is the natural path to Windows/macOS support.

8.Milestones & Phases

Phase 0 — Spike & validation (weekend)

Goal: de-risk the unknowns on real hardware before writing product code.
  • Enumerate S24 Ultra cameras via a scratch app: logical/physical IDs, max resolutions, fps ranges.
  • Prove pipeline: CameraX → MediaCodec surface → dump H.264 to a file → play with ffplay.
  • Prove transport: LocalServerSocket + adb forward → pipe raw H.264 → ffplay -f h264 -i tcp://… and eyeball latency.
  • Prove sink: ffmpeg → v4l2loopback → OBS manually.
  • Baseline comparison: try Android 14 native webcam mode + scrcpy --video-source=camera --v4l2-sink; record quality/latency numbers to beat.

Phase 1 — MVP (2–4 weeks)

Goal: the one-command experience, rear wide camera, 1080p30.
  • Android app: preview UI, foreground service, encoder, video socket, handshake.
  • openlens-cli: adb orchestration, decode, v4l2 write, reconnect.
  • Protocol v1 frozen (video channel + start/stop control).
  • README with setup guide (udev/adb, v4l2loopback, OBS screenshots).
  • Tag v0.1.0; APK via GitHub Releases + CI (GitHub Actions: gradle build, cargo build, clippy, ktlint).

Phase 2 — Camera controls & quality (2–3 weeks)

  • Lens switching (ultrawide/wide/3x/5x), zoom, torch, exposure compensation, tap-to-focus — from both phone UI and CLI flags.
  • 1080p60 and 4K30 modes; adaptive bitrate on thermal throttle.
  • Rotation handling; portrait/landscape negotiation.
  • Latency tuning pass with measured numbers (flash-to-photon test) published in docs.

Phase 3 — Reach (3–4 weeks)

  • Wi-Fi transport (mDNS discovery + QR pairing; same protocol over TLS-wrapped TCP).
  • Audio channel (phone mic → Opus → PipeWire virtual source on Linux).
  • F-Droid submission (reproducible build, no proprietary deps — mind this from day one).
  • Optional: native OBS plugin; Windows/macOS virtual camera sinks.

10.Risks & Mitigations

ADB dependency UX: non-dev users won't have USB debugging on. Acceptable for the v1 audience (streamers/tinkerers); document enabling it with screenshots, and keep Wi-Fi mode on the roadmap as the mainstream path.
Samsung hides physical lenses: if only the logical camera is exposed to third-party apps, ship with logical-camera zoom (which Samsung maps across lenses internally) — Phase 0 spike answers this.
v4l2loopback friction: needs a kernel module (DKMS). Mitigate with --setup guidance, distro-specific docs, and clear detection of "module loaded but wrong options".
Latency creep: buffering can hide in the encoder, socket, decoder, and v4l2 consumer. Measure at every phase (timestamp overlay + high-fps capture of both screens); never merge a change that regresses the glass-to-glass number.
Competing with "good enough" (native Android 14 webcam): the pitch must stay sharp — higher resolutions, bitrate control, lens selection, OBS-oriented features, and open source. Keep a comparison table in the README honest and current.

11.Licensing & Community

  • License: Apache-2.0 (permissive, patent grant, F-Droid compatible). If you study scrcpy's source closely, note it's Apache-2.0 too — compatible. GPL-3.0 is the alternative if you want copyleft; decide before first release.
  • FFmpeg linkage: dynamic-link LGPL builds of libavcodec to keep the Apache story clean; H.264 decoding via system FFmpeg sidesteps shipping codec code.
  • CONTRIBUTING.md, issue templates (device-report template is gold for a hardware-diverse project), CI on every PR, tagged releases with prebuilt CLI binaries + APK.
