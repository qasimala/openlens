Wi-Fi Implementation Review — verified against the running device

Static review of both codebases plus live testing on the reference S24 Ultra (R5CX30Z3G9J, 10.0.0.4) and CachyOS host (10.0.0.16), 2026-08-10.

1.Headline

fixedThe critical pairing vulnerability from my plan review is genuinely and correctly fixed. The grindable-SAS flaw is gone, replaced by a correct commit-before-reveal construction. I verified this three independent ways: reading both implementations, confirming cross-language test vectors agree (identical inputs → SAS 141454 in Kotlin and C++), and an independent agent recomputing the vectors in Python. The old ADB abstract-socket camera-theft path is deleted outright, not merely gated — stronger than I recommended.
blockerBut the Wi-Fi path does not work end to end. Pairing fails on real hardware, reproducibly (3/3 attempts). Separately, a file-descriptor double-close in the desktop streaming path would break every stream even if pairing succeeded. The release ledger is honest that every Wi-Fi gate is NOT RUN — this review confirms why that matters: the happy path has never executed.

3.Blocker: pairing fails on real hardware

Reproduced three times, including immediately after a fresh app launch (so the 120 s pairing window was open) with both devices on the same /24 and the app in the foreground.

desktop: openlens: secure connection to the phone failed:
         error:0A000126:SSL routines::unexpected eof while reading

phone UI: Read error: ssl=0xb4000072ddeacf18: I/O error during system call, Try again

Diagnosis: both error strings reference a live ssl= handle and a read, so the mutual TLS handshake completes and the failure is in the application exchange that follows. Both endpoints block reading, the phone's socket read times out (EAGAIN → "Try again"), it closes, and the desktop then sees EOF. That is the signature of a deadlock in the greeting / PAIR1 step, not a crypto failure — the commitment logic is never reached.

Worth checking first: the desktop writes the greeting "PAIR 2\n" then immediately blocks reading PAIR1 (wifi_transport.cpp:420-421); the phone reads the greeting and is expected to send PAIR1 (WifiHostController.kt:251-303). Confirm the phone actually reaches the send — the most likely culprits are the greeting line never satisfying the phone's line reader, or the phone waiting on a UI/arm condition before replying. Instrumenting both sides with a byte-level trace will localise it in minutes.

No app-level exception appears in logcat; the error is caught and surfaced to the UI, which is good error handling — but it means the stack trace is lost. Consider logging the caught exception at WifiHostController.kt:277.

4.Major findings

4.1 Pairing/listening is tied to activity lifetime, not visibility major

The plan requires (its §5.4, §7.2) that the phone advertise and accept pairing only while the pairing UI is visible. I measured the opposite: with the app backgrounded (launcher resumed) and the screen off, the phone continued advertising pair=1 and its TLS listener still accepted connections. Root cause (confirmed statically): the controller is created in onCreate and lives to onDestroy, and pairingWindowDeadline is set at construction — so it is bound to activity lifetime, not onStart/onStop.

Impact is bounded — pairing still needs on-phone confirmation, so this is not remote camera access — but the TLS handshake, pairing state machine and protocol parser stay exposed to the whole LAN while the user believes the app is closed, and the documented threat model is wrong. Move start/stop to onStart/onStop.

A corollary bug: because the window is armed once at construction and never re-armed, pairing becomes impossible 120 s after launch with no recovery except restarting the activity.

4.2 File-descriptor double-close breaks every stream blocker

ConnectedTls (wifi_transport.cpp:195-208) declares a destructor that unconditionally ::close(descriptor) but defaults its move constructor, which copies the int without resetting the source. connect_wifi_stream (:469) moves the object twice, so two objects destruct holding the same live fd. Consequences: the socket is closed before the caller reads (instant "disconnect"), and the released fd number can be reused by another thread while SSL still writes to it. Fix: reset other.descriptor = -1 in a hand-written move, or wrap the fd in a move-aware type.

4.3 Permissive TLS trust is not scoped to the pairing window major

Both sides use one permissive TLS context for every connection — desktop SSL_CTX_set_verify(..., SSL_VERIFY_NONE, ...) (wifi_transport.cpp:191) serving both pairing and normal sessions; Android a single X509TrustManager that accepts any non-empty chain (WifiHostController.kt:136-142). Authentication is still correct — both enforce the pinned SPKI with a constant-time compare immediately after the handshake, and I found no path where a normal session accepts an unpinned certificate. But the design called for a separate strict context, and the Android checkServerTrusted is an empty method: currently unreachable (the phone never acts as a TLS client), yet it becomes critical the moment anyone uses that context for an outbound socket. Make it throw.

4.4 Pairing denial-of-service major

Android: on desktop cancel/disconnect the confirmation wait can stall the full 30 s (up to ~60 s total) while holding pairingInProgress; with a 5-attempt cap in a 120 s window, an attacker who connects and immediately cancels can consume the entire pairing window. Desktop: no overall pairing deadline at all — the per-syscall timeout plus byte-at-a-time reads (ssl_read_line) let a peer dribble one byte every 44 s and hold the thread indefinitely; there is also no confirm timeout and no attempt cap.

4.5 All five ADB-era defects are still present major

These survived the migration unchanged in session.cpp/media.cpp:

  • Error paths skip END_STREAM and sink.stop() (leaks on the GUI's long-lived sink).
  • Sink exceptions counted as decode_errors, hiding V4L2 failures.
  • Missing AV_INPUT_BUFFER_PADDING_SIZE — FFmpeg may over-read up to 64 bytes past an attacker-controlled buffer. This is the one memory-safety issue and should be fixed regardless of anything else.
  • VIDEO_CONFIG still fed as a frame packet instead of extradata (the startup decode errors).
  • AV_CODEC_FLAG_LOW_DELAY / thread_count set after avcodec_open2 — no-ops, so the low-latency decode configuration is not actually in effect.

5.Minor

  • busy is hard-coded to "0" in the TXT record and never updated, though the desktop reads it.
  • Desktop private key is created world-readable and chmoded to 0600 afterwards — small but real window. Use open(..., 0600).
  • Peer file has no fsync before rename; a crash can silently unpair every device, which downgrades to a fresh trust-on-first-use prompt.
  • The pairing confirm dialog shows only the code — no device name or id — so a rogue device advertising a victim's id silently overwrites the stored pin if the user confirms.
  • The stable id UUID is broadcast in cleartext on every network joined — a durable cross-network tracking beacon. Consider rotating or advertising only while foregrounded.
  • POST_NOTIFICATIONS is not requested, so the foreground-service notification (the user-visible "camera is live" signal) can be suppressed on Android 13+.
  • Release build has no R8/minification; Log.e with exception detail ships.
  • Stale UI string "Dropped before USB"; stale usbStatus_ identifier in the GUI.
  • I observed a transient duplicate mDNS registration (two live listeners, same device id, ports 35399 + 39943). I could not reproduce it by re-launching, so I report it as observed-but-unexplained rather than a confirmed leak. The CLI deduped correctly.

6.Recommended order of work

  1. Root-cause the pairing deadlock (§3) — nothing else can be validated until the happy path runs.
  2. Fix the fd double-close (§4.2) — streaming cannot work without it.
  3. Fix the FFmpeg padding over-read (§4.5) — memory safety on attacker-controlled input.
  4. Move advertising/pairing to onStart/onStop and make the window re-armable (§4.1).
  5. Add pairing deadlines/attempt caps on the desktop; fix the Android confirmation stall (§4.4).
  6. Split strict vs permissive TLS contexts; make checkServerTrusted throw (§4.3).
  7. Then re-run the physical gates — discovery already passes, so pairing → stream → OBS is the remaining chain.
