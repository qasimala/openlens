2.Goals, MVP, and Acceptance Gates

MVP promise: Install the APK and the desktop package, connect the S24 Ultra over USB with debugging approved, press Start on the phone, and add the phone as a source in OBS — stable 1080p30 SDR with automatic reconnect, no account, no internet, no watermark.

In beta scope

  • Android APK, minSdk 31, developed and certified on the S24 Ultra first.
  • USB transport via the user's installed Android Platform Tools (adb).
  • Desktop: Linux. Both sinks: phonecam-cli + v4l2loopback (fast path/fallback) and the native OBS source plugin (flagship).
  • H.264/AVC 8-bit SDR: 720p30 and 1080p30 promised; 720p60 if capability tests pass.
  • Controls: rear/front, logical-camera zoom, autofocus + tap-to-focus, exposure compensation, torch, rotation, mirror.
  • Automatic reconnect (cable pull, app restart, OBS source reactivation) with placeholder UX.
  • Local-only: no telemetry, no cloud, loopback-only sockets, diagnostics with redacted support bundle.

Deferred (with release slots — see §7)

Audio (0.2-ish, may slip) · Windows (0.2) · 1080p60/4K/HEVC (0.3) · Wi-Fi (0.4) · macOS (0.5) · system-wide virtual webcam beyond Linux, HDR, iOS (post-1.0).

Beta acceptance gates (hard, measured)

Latency is measured glass-to-OBS with a millisecond timer/LED filmed simultaneously by the phone and a high-frame-rate reference camera. Encoder timestamps and subjective feel do not count. The harness output is a tracked per-release metric; a change that regresses median latency does not merge.

4.Protocol v0.1 (merged spec)

Single multiplexed TCP stream. Big-endian binary envelope (Codex framing), JSON control payloads (Claude), normative spec lives in protocol/protocol.md with golden valid/malformed fixtures.

Envelope (fixed 34-byte header):
  magic        4 B   "PHCM" — rejects misaligned/accidental input
  version      2 B   major.minor; incompatible major ⇒ clean failure
  type+flags   2+2 B message kind · KEYFRAME | CONFIG | END_OF_STREAM
  stream_id    4 B   separates restarted streams; reserves audio
  sequence     8 B   loss/duplication/reconnect-boundary detection
  pts_us       8 B   monotonic microseconds (never wall clock)
  length       4 B   validated against hard max BEFORE allocation
  payload      var   control JSON · capabilities · codec extradata · one access unit

Messages: HELLO, CAPABILITIES, CONFIGURE, CONFIGURED, VIDEO_CONFIG,
          VIDEO_FRAME, CONTROL, CONTROL_ACK, STATS, PING, PONG,
          ERROR, END_STREAM

Control payload examples (JSON, low-frequency only):
  {"cmd":"set","zoom":2.0}
  {"cmd":"set","torch":true}
  {"cmd":"switch_camera","facing":"front"}
  → CONTROL_ACK: {"requested":2.0,"applied":2.0}   // or applied + reason if clamped/unsupported

Invariants (all adopted)

  • A new stream_id always begins VIDEO_CONFIG + keyframe before dependent frames.
  • Unknown optional message types are skipped; unknown required types end the session with a version error.
  • Every control ACK carries requested value, applied value, and a failure reason when unsupported.
  • Hard-coded maximum payload size and dimensions on both sides; phone input is untrusted on the desktop.
  • No unbounded waits — cancellation interrupts socket reads, decoder waits, and adb child processes.
  • Fixtures cover truncated headers, oversized frames, reordered sequences, duplicate config, corrupt H.264 — and feed the fuzzer.

Connection flow

  1. User opens the app, grants camera permission, picks a (capability-verified) preset, presses Start → app listens on loopback, shows Waiting for desktop.
  2. Desktop enumerates adb devices; exactly one authorized target or an explicit serial selection.
  3. Desktop forwards a free host loopback port to the fixed device port, connects, sends HELLO.
  4. Phone replies CAPABILITIES → CONFIGURE/CONFIGURED → starts Camera2 + encoder → VIDEO_CONFIG → frames.
  5. Heartbeat both ways; on failure both sides tear down codec/socket cleanly and enter a bounded exponential reconnect (cap 5 s).
Security boundary: ADB authorized-computer trust + explicit Start on an unlocked phone is the MVP boundary. Loopback-only on both ends, reject second clients, remove the forward rule at shutdown, never fall back to LAN silently, no shell interpolation of device-provided text.

5.Android App

  • Stack: Kotlin, Gradle Kotlin DSL, Jetpack Compose, coroutines, immutable session state. minSdk 31, current stable targetSdk.
  • Modules: app (UI/permissions/foreground service) · camera (Camera2 capability inventory + session engine) · encoder (MediaCodec config/output) · protocol (wire format, shared fixtures with desktop).
  • Pipeline: one Camera2 repeating request targeting preview surface + encoder input surface; TEMPLATE_RECORD, continuous video AF, constant FPS range. Encoder: surface color input, repeat-config after reconnect, KEY_REPEAT_PREVIOUS_FRAME_AFTER for static scenes, low-latency flag where supported.
  • Lens model: enumerate logical + physical cameras, focal lengths, zoom ratio range, per-size FPS, stabilization, torch, manual ranges. Prefer smooth logical-camera zoom on Samsung; promise direct physical-lens selection only where the device demonstrably honors it (Phase 0 answers this for the S24U).
  • Timestamps: monotonic µs PTS from the capture pipeline; timeline resets only on explicit stream restart (new stream_id).
  • Lifecycle: streaming starts only from a visible user action; camera-type foreground service with permanent notification for background/screen-off streaming; "dim preview while streaming" and "keep streaming on lock" as separate toggles; verify Samsung power management empirically, don't assume.
  • UI states: No permission → Ready → Waiting for desktop → Streaming → Recovering → Error; every error names a user action. Developer stats overlay: requested/actual fps, bitrate, keyframes, encoder name, thermal status (getThermalHeadroom).
  • Thermals: surface temperature state in UI; in MVP degrade only via explicit one-click prompt ("Phone is hot — switch to 720p30?"), never silently.

6.Desktop: Core, CLI, OBS Plugin

Shared core (one implementation, two consumers)

  • ADB manager: locate adb (PATH + picker), parse adb devices -l, model ready/offline/unauthorized states, require serial choice for multiple devices, own only this app's forward rule, capture actionable stderr. Redact serials in logs by default.
  • Transport: bounded reads, version negotiation, max-frame checks, heartbeat, cancellation, exponential reconnect capped at 5 s.
  • Decode: libavcodec H.264 software first (trivial at 1080p30), VAAPI as a later optimization; output NV12/I420 with color range/matrix preserved.

phonecam-cli (Phase 2 deliverable, permanent)

phonecam-cli list      # adb devices + auth state
phonecam-cli probe     # phone capabilities via HELLO/CAPABILITIES
phonecam-cli receive   # decode → v4l2loopback (or null sink / stats only)
phonecam-cli doctor    # whole-path validation: adb, device, app, socket, decode
# --json on every verb for CI · optional Annex-B dump only when explicitly requested

The v4l2 sink auto-detects an existing loopback device; doctor prints the exact modprobe v4l2loopback exclusive_caps=1 card_label=… commands rather than silently escalating.

OBS plugin (Phase 3 deliverable, flagship)

  • Built from the official obs-plugintemplate toolchain; pinned OBS compatibility range; explicit license provenance.
  • One async video source, Phone Camera; each source instance owns a session via the shared core.
  • Properties: device (privacy-safe label), preset, bitrate, camera, mirror, rotation, buffer mode, read-only status panel; advanced codec values behind an Advanced section.
  • ≤2-frame queue in low-latency mode; correct timestamp/format/colorspace/range on every published frame.
  • Reconnect UX: last good frame ≤2 s, then a clear "Disconnected" placeholder; reconfigure cleanly at next keyframe on resolution/rotation change; "stop when hidden" configurable (default: keep running for instant scene switches).
  • Test native distro OBS package first; document Flatpak sandbox limitations (host adb access) separately.

7.Roadmap

Estimates assume one experienced developer, one S24 Ultra, an existing Linux + OBS setup. Each phase is independently demonstrable; no polish while the previous phase's exit criteria fail.

Phase 0 — Feasibility, baselines, naming (2–3 days)

  • Record reference environment: distro, OBS version + package type, cable, Android/One UI version.
  • Capability dump on the S24U: camera IDs, physical IDs, focal lengths, sizes/FPS, encoder profiles, bitrate modes. Answers the Samsung physical-lens question.
  • scrcpy camera → v4l2 baseline: setup time, latency, CPU, thermals, failure behavior. Also try Android 14 native USB webcam mode as a second baseline.
  • Throwaway Camera2 → MediaCodec probe at 1080p30 + 720p60; validate Annex-B with FFmpeg for 30 min.
  • Manual v4l2loopback + ffmpeg → OBS test to lock sink parameters.
  • Naming search; pick a non-conflicting public name before any package IDs.
  • ADR-001 (sink strategy: CLI/v4l2 then plugin), ADR-002 (custom ADB protocol), ADR-003 (core language — the v3 decision, recorded).

Exit: valid hardware H.264 off the S24U for 30 min; baselines documented; stop/reframe checkpoint: if the scrcpy baseline already delivers an equally good OBS experience and a native source can't materially improve setup, controls, or reliability, reframe as an OBS-integration-for-scrcpy project instead of duplicating its transport.

Phase 1 — Android capture engine (4–6 days)

  • Scaffold modules, lint/format, unit tests, CI APK build.
  • Permission flow, capability inventory, supported-preset model, Camera2 preview.
  • Camera2 → MediaCodec surface → timestamped access units.
  • Controls: rear/front, zoom, AF/tap-to-focus, exposure comp, torch, mirror metadata, rotation policy.
  • Foreground service, notification, clean Stop, backgrounding + screen-lock behavior on Samsung.
  • Developer stats overlay incl. thermal status.

Exit: APK produces decodable 1080p30 for one hour; controls apply without restart unless technically required; backgrounding doesn't corrupt the stream.

Phase 2 — Protocol + desktop vertical slice (5–7 days)

  • Freeze protocol v0.1; golden fixtures + fuzzer target.
  • Android loopback server: handshake, control ACKs, heartbeat, single-client rule, bounded write queue.
  • Desktop core: adb discovery/forward, parser, reconnect state machine, stats. (Language decision from v3 lands here.)
  • phonecam-cli all four verbs; decode via libavcodec → v4l2loopback sink. First live-in-OBS moment via the V4L2 source.
  • Failure matrix: unauthorized, offline, multi-device, app-not-running, cable pull, truncated stream, codec reset.
  • Latency harness built now; tune encoder/keyframe/socket buffering before plugin work.

Exit: one command yields live S24U video in OBS (v4l2 path), survives cable pulls, passes malformed-input tests, provisional median latency ≤150 ms.

Phase 3 — Native OBS plugin alpha (7–10 days)

  • Template-based scaffold, pinned OBS range; source registration and safe lifecycle/cancellation.
  • Decoded frames with correct color metadata; device/preset/control properties; live status panel.
  • Reconnect + placeholder UX; scene switches, hide/show, duplicate sources, deletion, OBS shutdown, recording, streaming.
  • Linux installer/archive + uninstaller that never touches unrelated OBS files.

Exit: clean Linux machine installs the plugin, adds Phone Camera, records 60 min of 1080p30, recovers from cable pull without restarting OBS — and beats or matches the v4l2 path on latency.

Phase 4 — Reliability, UX, (audio) (5–8 days; audio may slip)

  • 2-hour soak, thermal, low-battery, lock-screen, app-switch, repeated-reconnect tests against the §2 gates.
  • Support bundle + log redaction, placeholder frames, troubleshooting copy, error-language table implemented.
  • Audio (if it fits): AudioRecord, same monotonic clock, distinct stream_id, jitter correction, 2-hour lip-sync drift validation, user latency/offset controls. Codec (Opus vs AAC-LC) decided by measurement.
  • Accessibility pass: TalkBack, scalable text, color-independent states, keyboard nav in plugin properties.

Exit: all beta gates pass on the S24U; every error state is actionable; audio is demonstrably synchronized or explicitly excluded.

Phase 5 — Public beta + community foundation (4–6 days)

  • License review (split-license model, SPDX inventory, notices, headers) signed off.
  • Docs: setup, building, architecture, privacy, troubleshooting, contributing, security, releases. Honest comparison table vs scrcpy / native webcam / DroidCam.
  • Signed APK + plugin + CLI, SHA-256 checksums, SBOM, reproducible notes from CI. DCO sign-off, issue forms (device-report form is gold), labels.
  • Device matrix before "general-purpose" claims: one Samsung flagship, one Pixel, one mid-ranger. F-Droid submission prep (no proprietary deps — enforced from day one).

Exit: 0.1.0 builds from source, installs from signed artifacts, is supportable via documented diagnostics, and is contributable without private knowledge.

8.Testing & Measurement

  • Android: capability→preset selection/fallback, camera/encoder state machine + cancellation, protocol encode/decode + timestamp/queue bounds, permission and foreground-service lifecycle, fake encoded source for deterministic transport tests.
  • Desktop: parser unit tests + fuzzing under a strict memory limit; golden H.264 sequences; fake adb outputs for offline/unauthorized/multi-device; reconnect/cancellation race tests under sanitizers (or Miri/loom if the core is Rust); color conversion and timestamp monotonicity tests.
  • Physical matrix (evidence retained per run): quality modes, controls (applied-value logs), reliability (2 h stream, 50 start/stops, 20 cable pulls, OBS restart, screen lock), performance (CPU/GPU/battery/temperature/USB throughput), latency (static, motion, low light, post-reconnect, while recording+streaming), failure UX (time-to-recovery), privacy (packet capture proving zero LAN/internet traffic in USB mode; redaction check on the support bundle).
  • CI: per-change format/lint/unit/native build/sanitizer/protocol-compat/license scan; protocol-fixture changes must state compatibility impact and update the spec; nightly fuzz corpus + artifact install smoke test in a clean container; release tags require the manual S24U acceptance checklist — green CI alone never promotes a release.
  • Standing rule (kept from Claude v1): the latency harness result is a tracked metric; changes that regress the median do not merge.

9.Licensing, Naming, Community

  • Licensing (proposed, needs v3 sign-off): Apache-2.0 for android/, desktop/core, desktop/cli, protocol/; GPL-2.0-or-later for desktop/obs-plugin/ (links libobs). One-way flow rule: core → plugin only. FFmpeg: dynamic-link LGPL builds. Full SPDX dependency review before the first public tag. Study scrcpy, don't copy it in the first implementation; if code is ever reused, preserve Apache-2.0 notices and re-run the review.
  • Naming: "openlens" is a codename only (Kubernetes-IDE collision). Naming search + package/domain screening in Phase 0, before applicationId/plugin IDs exist.
  • Privacy promises (published in README): no account/ads/analytics/cloud/required internet; loopback-only USB mode behind ADB authorization; streaming never starts hidden — persistent notification whenever the camera is live; no automatic capture files; redacted local-only support bundles; signed artifacts + checksums + SBOM; least-privilege CI.
  • Community: LICENSE/NOTICE, README with 60-second value prop + honest status + comparison table, CONTRIBUTING, CODE_OF_CONDUCT, SECURITY with private reporting, DCO (no CLA), issue forms (bug / device compatibility / feature / security redirect), labels incl. good first issue and device compatibility.

11.Open Questions for v3

Everything else in this document is proposed as settled. These need a verdict in v3:

  1. Desktop core language (ADR-003).
